# کد معرف — سند تحویل

> **این سند خروجی فاز طراحی است و تصمیم‌ها در آن بسته شده‌اند.** هر «چرا»یی که
> این‌جا نوشته شده، برای این است که دوباره باز نشود — نه برای این‌که دوباره
> ارزیابی شود. **هیچ‌کدام از تصمیم‌های بخش ۲ را عوض نکن.** اگر جایی از سند
> ابهام داشت یا با کدِ واقعی نخواند، **بایست و بپرس — حدس نزن.**
>
> این سند **کد نمی‌نویسد**؛ می‌گوید چه چیزی کجا و چرا. الگوی هر تکه را از
> نزدیک‌ترین همسایه‌اش در همان فایل بردار (این ریپو با تقلید از همسایه کار
> می‌کند، نه با اختراع).

---

## ۱. در یک بند

هر کاربر ثبت‌نام‌کرده می‌تواند یک **کد معرف** بسازد: یک نامِ لاتینِ دلخواه
(۴ تا ۱۶ حرف) که سیستم **دو رقم آخر موبایلش** را به تهش می‌چسباند — مثل
`dentmaster61`. هر کسی که این کد را **در صفحه‌ی پرداخت و روی اولین خرید واقعی‌اش**
وارد کند **٪۱۰** تخفیف می‌گیرد، و صاحب کد **٪۵** اعتبار یک‌بارمصرف. اعتبارِ
معرف **سقف انباشت ندارد** (۴۰ معرفی = ٪۲۰۰) اما در هر خرید حداکثر **٪۱۰**‌اش
اعمال می‌شود و بقیه برای خریدهای بعد می‌ماند — و اگر صاحب کد **«ستون»** باشد،
٪۲۰ دائمیِ ستون روی همان ٪۱۰ می‌نشیند و می‌شود **٪۳۰**.

## ۳. مقادیر و فرمت

```
درصد معرَّف (کسی که کد را می‌زند):   ٪۱۰
درصد معرف   (صاحب کد):              ٪۵
سقف مصرف در هر خرید:                ٪۱۰   (CREDIT_CAP_PERCENT — دست نخورد)
تخفیف ستون:                          ٪۲۰   (جدا، روی سقف می‌نشیند)
حداکثر ممکن برای یک نفر در یک خرید:  ٪۳۰
```

**فرمت کد:** `[a-z]{4,16}` + دو رقم → `dentmaster61`، `dens61`. ذخیره و مقایسه
همیشه با حروف کوچک.

**نرمال‌سازی ورودی هنگام مصرف** (کاربر از تلگرام کپی می‌کند، رقم فارسی تایپ
می‌کند، فاصله جا می‌گذارد):

1. `trim` + حذف همه‌ی فاصله‌ها و ZWNJ (`‌`)
2. تبدیل ارقام فارسی/عربی به لاتین — **تابعِ `toLatinDigits` را از
   `services/phone.ts:10` بیرون بکش و export کن؛ کپی دوم نساز**
3. `toLowerCase()`

**درصدها کجا زندگی می‌کنند:** دو ثابتِ export‌شده در `services/referrals.ts`،
دقیقاً به سبکِ `PILLAR_DISCOUNT_PERCENT` در `pillar.ts:76`. تنظیم دوباره‌شان
یک کامیت + دیپلوی است، و به لطف تصمیم ۲.۳ **روی اعتبارهای قبلی اثر ندارد**.

## ۴. مهاجرت `0044_referrals.cjs`

آخرین مهاجرت `0043_bank_transfer.cjs` است، پس این یکی **۰۰۴۴**. **قبل از
کامیت دوباره چک کن که ۰۰۴۴ آزاد است** — `scripts/repair-migration-ledger.cjs`
مستند می‌کند که در ۱۴۰۵/۰۵/۲۰ دو شاخه هر دو `0037` را ساختند و پروडکشن وارد
crash-loop شد.

سبک فایل: کامنت بلندِ ابتدای فایل که **تصمیم** را توضیح می‌دهد نه DDL را
(الگو: `0041`, `0042`, `0043`)، بعد `exports.shorthands = undefined`،
`exports.up`/`exports.down` با `pgm.sql()` خام و `down` معکوس با `if exists`.

```sql
create table referral_codes (
  user_id    uuid primary key references profiles(id) on delete cascade,
  alias      text not null,
  code       text not null unique,
  created_at timestamptz not null default now(),
  check (alias ~ '^[a-z]{4,16}$'),
  check (code  ~ '^[a-z]{4,16}[0-9]{2}$')
);

create table referrals (
  id               uuid primary key default gen_random_uuid(),
  -- یکتا: هر حساب در تمام عمرش فقط یک بار معرفی می‌شود (تصمیم ۲.۶)
  referred_user_id uuid not null unique references profiles(id) on delete cascade,
  referrer_user_id uuid not null references profiles(id) on delete cascade,
  -- کد همان‌طور که مصرف شد، برای سابقه؛ منبع حقیقتِ مالکیت referrer_user_id است
  code             text not null,
  -- درصدها اینجا مهر می‌شوند تا تغییر ثابت‌ها اعتبارِ کسب‌شده را عقب نبرد (تصمیم ۲.۳)
  referred_percent int not null check (referred_percent between 1 and 100),
  referrer_percent int not null check (referrer_percent between 1 and 100),
  created_at       timestamptz not null default now(),
  check (referrer_user_id <> referred_user_id)
);
-- «چند نفر با کد من آمدند» و مشتق‌کردن اعتبارِ معرف
create index on referrals (referrer_user_id);
```

## ۵. `services/referrals.ts` (فایل جدید)

کامنت ابتدای فایل باید تصمیم‌های ۲.۲، ۲.۳، ۲.۴ را توضیح دهد — الگو:
`services/pillar.ts`.

```ts
export const REFERRED_DISCOUNT_PERCENT = 10;
export const REFERRER_DISCOUNT_PERCENT = 5;
export const ALIAS_RE = /^[a-z]{4,16}$/;

export function normalizeCode(raw: string): string;

/** کد این حساب، یا null اگر هنوز نساخته. */
export async function myCode(userId: string, client?: Queryable): Promise<ReferralCode | null>;

/** ساخت یک‌باره. دو رقم از phone یا (اگر phone نبود) تصادفی. */
export async function mintCode(userId: string, alias: string):
  Promise<{ ok: true; code: string } | { ok: false; reason: MintRefusal }>;

export type MintRefusal = 'bad_alias' | 'already_has_code' | 'code_taken';

export type ClaimRefusal =
  | 'unknown_code'       // چنین کدی نیست
  | 'own_code'           // کد خودش
  | 'already_referred'   // قبلاً از یک کد استفاده کرده
  | 'already_purchased'; // قبلاً خرید موفق داشته (تصمیم ۲.۵)

/** فقط بررسی — هیچ چیز نمی‌نویسد. برای پیش‌نمایش صفحه‌ی پرداخت. */
export async function checkClaim(userId: string, code: string):
  Promise<{ ok: true; referrerId: string; code: string } | { ok: false; reason: ClaimRefusal }>;

/** بررسی + نوشتن ردیف. idempotent: اگر همین ردیف هست، همان را برمی‌گرداند. */
export async function claimReferral(userId: string, code: string):
  Promise<{ ok: true; referral: Referral; created: boolean } | { ok: false; reason: ClaimRefusal }>;

/** آمار صاحب کد — فقط عدد، بدون اسم (تصمیم ۲.۱۳). */
export async function referralStats(userId: string): Promise<ReferralStats>;
```

**نکته‌ی `mintCode`:** بین «کد آزاد است؟» و `insert` مسابقه هست. روی خطای
یکتایی (`23505`) `code_taken` برگردان — مثل حلقه‌ی retry در
`gift-redemption.ts:144-157`، ولی بدون retry (نام را کاربر انتخاب کرده،
نمی‌شود جایش تصمیم گرفت).

**نکته‌ی `claimReferral` و idempotency:** `referred_user_id` یکتاست، پس
`on conflict (referred_user_id) do nothing` + یک `select` بعدش. اگر ردیفِ
موجود **معرفِ دیگری** داشت، `already_referred` برگردان — نه اینکه بی‌صدا
معرف را عوض کنی.

## ۶. `services/discount-credits.ts` — منبع سوم

1. `DiscountCredit['kind']` را از `'badge' | 'grant'` به
   `'badge' | 'grant' | 'referral'` بزرگ کن. **چک شده: هیچ‌جای ریپو روی این
   فیلد `switch`/شرط ندارد؛ فقط برچسب است.**
2. تابع جدید، دقیقاً هم‌شکلِ `grantCredits`:

```ts
export async function referralCredits(
  userId: string, client: Queryable = pool,
): Promise<DiscountCredit[]>
```

با **یک** کوئری که هر دو سمت را می‌دهد:

```sql
-- سمت معرَّف: همیشه، از لحظه‌ی ثبت ردیف
select 'referral:' || r.id as source, r.referred_percent as percent,
       'تخفیف معرفی' as label_fa
  from referrals r
 where r.referred_user_id = $1
union all
-- سمت معرف: فقط وقتی معرَّف واقعاً پول داده (تصمیم ۲.۴)
select 'referral_bonus:' || r.id, r.referrer_percent, 'پاداش معرفی'
  from referrals r
 where r.referrer_user_id = $1
   and exists (select 1 from payments p
                where p.user_id = r.referred_user_id and p.status = 'paid')
```

> دو پیشوندِ متفاوت روی یک `id` عمدی است: دو اعتبارِ کاملاً جدا با دو
> spent-nessِ جدا، بدون ستون اضافه. ایندکسِ
> `payments_user_idx (user_id, created_at desc)` این `exists` را پوشش می‌دهد.

3. در `availableCredits` (خط ۲۰۷) `referralCredits(userId)` را به همان
   `Promise.all` اضافه کن و در خط ۲۱۱ به آرایه بچسبان. **همین. `pickCredits`،
   `spentSources`، `recordRedemptions` و سقف دست نمی‌خورند.**

## ۷. `services/payment.ts` — کمترین تغییر ممکن

`startPayment` یک پارامتر اختیاری `referralCode?: string` می‌گیرد. **جای
دقیقش: بعد از چک ظرفیت (خط ۱۰۴) و قبل از خواندن اعتبارها (خط ۱۳۴)** — چون
`availableCredits` باید ردیفِ تازه‌نوشته را ببیند.

```
capacity → [claimReferral اگر کد آمده] → pillarSeat → availableCredits → …
```

سه قاعده که نباید بشکنند:

- **`claimReferral` بیرونِ `try/catch`ِ اعتبارهاست.** آن `catch` (خط ۱۳۳-۱۳۷)
  عمداً می‌گوید «موتور تخفیف حق ندارد مغازه را بخواباند». ولی کدِ **نامعتبر**
  یک خطای ورودیِ کاربر است و باید به‌صورت ۴۰۰ برگردد، نه اینکه بی‌صدا قیمت
  کامل بگیریم. پس: رد شدنِ `claimReferral` → `StartResult` با
  `error: 'referral'`؛ افتادنِ `referralCredits` داخل همان catch قدیمی →
  فروش با قیمت کامل ادامه پیدا می‌کند (و یک `console.error` بلند).
- **ردیفِ `referrals` حتی اگر پرداخت رها شود می‌مانَد و درست است.** اعتبار ٪۱۰
  مصرف‌نشده باقی می‌ماند (چون spent-ness یک join روی وضعیت پرداخت است) و دفعه‌ی
  بعد اعمال می‌شود. هیچ مسیر پاک‌سازی لازم نیست.
- **`settlePayment` دست نمی‌خورد** جز یک خط fire-and-forget برای اعلانِ بخش ۹،
  دقیقاً کنار `schedulePillarWelcome` (خط ۳۶۳). ٪۵ معرف **مشتق** است؛ چیزی
  برای «minting» وجود ندارد.

## ۱۰. `services/merge-profiles.ts` — **اجباری، و اگر جا بیفتد بی‌صدا خراب می‌شود**

هر دو جدول `on delete cascade` به `profiles` دارند و `mergeProfiles` در
انتها ردیفِ مبدأ را **حذف می‌کند**. اگر این جداول به آن فایل اضافه نشوند،
ادغامِ دو حساب **تاریخچه‌ی معرفی و اعتبارِ مالیِ واقعی را بی‌سروصدا پاک
می‌کند**. سه حالت، و هر سه لازم‌اند:

1. **`referral_codes`** — کلید اصلی‌اش `user_id` است، پس اگر هر دو حساب کد
   داشته باشند تصادم می‌شود. الگوی `user_pathways` (خط ۳۱-۳۸): اول ردیفِ مبدأ
   را حذف کن اگر مقصد کد دارد، بعد بقیه را repoint کن. **کدِ مبدأ آزاد
   نمی‌شود و دوباره قابل ساخت نیست** — بیرون پخش شده است.
2. **`referrals.referred_user_id`** — یکتاست، پس اگر هر دو حساب معرفی‌شده
   باشند تصادم می‌شود. همان الگو: ردیف مبدأ حذف، بقیه repoint.
3. **`referrals.referrer_user_id`** — repoint ساده، **ولی بعدش**: اگر A، B را
   معرفی کرده بود و حالا A و B ادغام می‌شوند، `check (referrer <> referred)`
   می‌شکند. بعد از repoint، ردیف‌های خودمعرفی را حذف کن.
