### 4.11. Flashcards (Leitner) — semantic `DefinedTermSet` in the FAQ corpus

**Runs on every publish that produces a page — except LiteCast and DentCast+ (`dentcast_plus`)**, and a چالش (module 09). LiteCast stays outside the specialist ecosystem. **DentCast+ is optional, not skipped:** a video's content is in the recording, and the page text is often a one-line caption, so cards need the founder to supply the clinical tips; with that text, run normally; without it, record a documented skip, never a fabricated card (Hard Rule 13). `tools/verify_publish.py`'s `FLASHCARD_OPTIONAL_TYPES` reports the same two-type exception as a skip.

A flashcard is **a concept, not a question**, so it uses schema.org's vocabulary for that: `DefinedTermSet` → `hasDefinedTerm[]` of `DefinedTerm { name, description }`. It is written into **`plus/faq-corpus.json`, under the page's content id — never into the page's own JSON-LD** (hidden markup with no visible rendering is an SEO liability, `.dentcast/faq-schema-removal-handoff.md`; `verify_publish.py` fails a page whose HTML carries a `#flashcards`-tagged `DefinedTermSet`). `plus/flashcards-index.json` is generated by `node tools/build_flashcards_index.mjs` in the runner's C.8; never edit it. **This step never touches `dentcast-brain.json`** (Hard Rule 5).

**Card content must be semantic, never a mechanical FAQ dump.** Each `DefinedTerm` tests recall of **one concept**: `name` is a tight recall prompt, `description` the complete, precise answer to that one concept.

**"Verbatim" includes the near-copy — this step's most common failure.** Deleting the answer's verdict («بله؛ …» → «…») and shipping the rest, reordering a clause or swapping a word is **not** a rewrite. A FAQ answer argues a case *about this article*; a card states what a concept *is*, standing alone, for a reader meeting it cold months later. If the `description` still reads as an answer to its question, it has not been rewritten. Phase F fails a description that matches a FAQ answer with or without its verdict prefix.

**FAQ → flashcard compression, judged, not mechanical.** Where the corpus entry has a FAQPage node, classify each `mainEntity` Q/A pair:
- **"Define/explain X" shaped** → one `DefinedTerm`: the question rewritten into a `name` recall prompt, the answer into a complete `description`; an answer bundling several concepts becomes several atomic terms.
- **Comparison/decision/procedural** («ایمپلنت کوتاه یا سینوس لیفت؟», «کدوم بهتره؟») → no single concept: **skip** it and say so in the report.

Without a FAQ, author `DefinedTerm`s directly from the body by the same atomicity rule.

Node shape in `plus/faq-corpus.json`, under the content id's `definedTermSets` array:

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "DefinedTermSet",
  "@id": "https://dentcast.org/insight/insight-12.html#flashcards",
  "hasDefinedTerm": [
    {
      "@type": "DefinedTerm",
      "@id": "https://dentcast.org/insight/insight-12.html#flashcards-c1",
      "name": "single-concept recall prompt",
      "description": "complete, precise answer to that one concept",
      "source": "faq",
      "sourceFaqIndex": 2
    }
  ]
}
</script>
```

- Each `DefinedTerm` `@id` ends in `#flashcards-c<n>`, 1-indexed per page, **stable once published** — a later wording fix never renumbers (the backend's `card_state` rows key off the fragment).
- `source` is `"faq"` or `"authored"`; `sourceFaqIndex` is present **only** for `"faq"`, pointing at the FAQPage `mainEntity` index it came from.
- No other properties beyond real `DefinedTerm`/`DefinedTermSet` fields plus these two.

**Report:** the term count and `@id`s, `faq` vs `authored`, and which FAQ pairs were skipped as comparison/decision-shaped. Phase F (`4.11 cards`, `8 flashcards`) checks presence, unique sequential ids and the near-copy ban.

### 4.12. Quiz-ready FAQ + scored binary bank

**Runs on every publish that produces a page — LiteCast is the sole category exception** (a چالش also skips it, module 09). The FAQPage node — written into `plus/faq-corpus.json` under the content id, **never into the page's own JSON-LD** — feeds two premium surfaces: the flashcards (4.11) **and** a scored yes/no quiz (`plus/quiz-index.json`, premium XP). FAQ questions are therefore written to a **standalone-quiz standard**, with two hard requirements:

**(a) Self-contained — no article deixis.** A dentist who read the article a month ago and remembers only the concept must understand and answer it. **Forbidden in a question `name`:** «این کیس», «این بیمار», «این مطالعه», «این متن», «این ویدیو», «این تکنیک/روش/وضعیت/تصمیم/خطا», or any reference that resolves only on this page. Case-based content (chairside, insight cases, dentcast-plus videos) embeds the case's key conditions **into the question** — «چرا MTA برای این کیس انتخاب شد؟» becomes «در تحلیلِ خارجیِ سرویکالِ (ECR) پیشرفته، چرا MTA ماده‌ی مناسبی برای ترمیم است؟». Pure narrative recall of one unnamed patient («تصمیمِ نهایی برای این بیمار چه بود؟») does not belong in the FAQ. The answer stays 100% grounded in the body.

**(b) Binary answers open with an explicit verdict.** `tools/build_quiz_index.mjs` keeps a question only when it is yes/no-phrased (opens «آیا»/«مگر», or ends «… درست است؟» / «… امکان دارد؟» etc.) **and** its answer's **first clause** says «بله» or «خیر»/«نه». So a yes/no-shaped question's answer opens with the verdict — «خیر؛ …», «بله، …», or a short concession then the verdict («برخلافِ باورِ قدیمی، خیر؛ …»); that word is the graded key. A genuine "it depends" stays hedged and is correctly **excluded** from the scored bank (it still serves as flashcard/reference). Never contort it into a false yes/no — the bank must never grade against a guessed key.

The runner's C.8 runs `node tools/build_quiz_index.mjs` (never hand-edit `plus/quiz-index.json`); its `content_id` is the page path without `.html`, and each question keeps its `source_faq_index`, the same identifier convention as flashcards.

**When to run — and fix, not just flag.** At C.4.12, on the locked body, **before** the corpus entry is final, walk every `mainEntity` question and **bring it into compliance in place**: a question with deixis is rewritten standalone or removed; a yes/no answer that buries or omits the verdict is reopened with «بله»/«خیر». Edits stay inside the corpus entry's FAQPage node and the answer stays grounded in the body.

**Report:** how many binary questions the page contributes (zero → confirm its FAQ is intentionally open/comparison-shaped) and every question rewritten or dropped. Phase F (`4.12 quiz`) re-checks deixis and verdicts.

### 4.12-ب. سؤالِ آزمونِ مسیر برای همین مطلب — `plus/exam-questions.json`

**Runs on every publish whose page becomes (or already is) a step of a full pathway — every specialist type step 5.6 files into `plus/pathways.json`. Skipped, as a documented skip, for LiteCast, چالش, glossary terms and any publish whose page lands in no full pathway.** Membership is known only at step 5.6, so this step is **evaluated there, after placement** (module 10 triggers it). The pathway certificate exam draws article questions from two sources — the founder's rows in the API (`content_exam_questions`) and this repo file — so a question committed with the article is in every carrying pathway's pool with no panel step and no deploy. This step writes the repo half.

**What to write.** One to three **four-option multiple-choice** questions for this page, authored from the body (and the FAQ finalized in 4.12), to the standard of `reports/exam-questions-from-quiz-2026-10-25.md`:

- **Conceptual, not article-recall** — a dentist who knows the concept but never read this page can answer. Not a named study's number, not «what the authors concluded», not one patient's story. Textbook constants are fine.
- **Self-contained stem** (4.12(a)'s deixis ban); embed a case's key conditions when the concept holds only under them.
- **Exactly four options, one correct per the body**, three distractors that are *wrong according to the body* (not merely less complete), same grammatical form and category, comparable length (longest ≤ 1.25× the shortest), the key not the single longest, no «همهٔ موارد»/«هیچ‌کدام», no option restating the stem. Persian ی/ک, ZWNJ, the page's own ezafe style; Latin terms as the page writes them.
- **Never a yes/no question dressed as two options**, never a claim the body does not make, never an «it depends» forced into one key. When nothing passes this bar, write none and record the skip with its reason — a missing question costs nothing (every pathway opens on its own at twenty article questions).

**Message M2 — the founder approves every question in chat before it is written** (`publish-checkpoints.md`): stem, all four options, the key and one line on why the key is right per the body — **the full text, never a summary or a count**. Before showing them, run `python3 tools/validate_exam_questions.py --draft-check <draft.json>` (in the queue: `08-سؤال‌های-آزمون.json`): it fails a question without exactly four options, with lengths over 1.25×, whose key is the single longest option, with a «همهٔ موارد»/«هیچ‌کدام» option or an option restating the stem, warns when a stem word recurs only in the key (a leak), and prints the full text to show. Fix every ERROR and look at every leak WARN before asking. Write only what was approved; a question the founder wants kept «for later» goes in with `"status": "review"` and a `review_note`, which the API never draws.

**Where it goes.** Under the page's `content_id` in `plus/exam-questions.json` (`byContent[content_id].questions[]`), appended, never replacing existing rows. Each row:

```json
{
  "id": "r-<8 hex of sha1(content_id + '|' + a stable per-question handle)>",
  "kind": "mcq",
  "prompt_fa": "…",
  "options": ["…", "…", "…", "…"],
  "correct": 2,
  "source": "publish"
}
```

- `id` is **load-bearing and never re-minted** (attempt snapshots and the «unseen first» draw reference it) and carries the `r-` class so it never collides with a form's `qN` or a table row's `c-…`. Mint it from `sha1("<content_id>|publish-<n>")[:8]` with `n` the next free ordinal for the page; a later wording fix keeps the id.
- `correct` is the 0-based index; vary the key position across the page's questions (the API does not shuffle).
- `source` is `"publish"` (rows derived from the quiz bank carry `"quiz"` + `source_quiz_id`).

**Existing rows are append-only** — CI, the validator and Phase F's «4.12-ب bank» row FAIL when any existing row (this page's or another's) is deleted or changed, naming the lost `content_id#id`; retire a row with `"status": "rejected"`. Reordering only WARNs (ids, not positions, are load-bearing). The single exception is a fix the founder approves in chat for an existing row (wording, key): keep its `id`, edit the row, then record that approval for exactly the edited bytes in `.dentcast/exam-edit-approvals.json` (add it to `target_paths`):

```json
{
  "insight/insight-63#r-0123abcd": {
    "content_id": "insight/insight-63",
    "question_id": "r-0123abcd",
    "row_sha256": "<python3 tools/validate_exam_questions.py --row-sha256 insight/insight-63#r-0123abcd>",
    "approval": {"status": "confirmed", "decision": "exact scope of the fix",
                 "evidence": ["public-safe reference to the founder's approval"]}
  }
}
```

Any later change to that row needs a new approval and hash. `--allow-edit <content_id>` only previews a fix locally; CI and Phase F do not read it.

Then run `python3 tools/validate_exam_questions.py` (shape, ids, option rules, duplicate prompts; `verify_publish.py` reads it in its «4.12-ب exam» row). No builder: the file is hand-authored like `plus/pathways.json`, and `plus-api` re-fetches the published copy on its own (`EXAM_QUESTIONS_URL`, `content-refresh.ts`).

**Ledger:** this step has no checkpoint id and does not hold **C.4.12**, the module's second checkpoint (its evidence notes «4.12-ب: evaluated at 5.6»); its result (rows written, or the skip reason) goes into the evidence of **C.5.6**.

**Report:** how many questions the page added (or the skip reason), that each was approved in chat (M2), that `validate_exam_questions.py` passes, and which full pathways now draw them (`pathwaysContaining`, or read `plus/pathways.json`).
