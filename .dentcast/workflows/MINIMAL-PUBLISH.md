# Minimal Publish Path (no AI agent)

**Use this only when `.dentcast/workflows/README.md` (the ~70-step router) is
not executable — no agent available to run it.** This path gets one Persian
page **live, indexable, and reachable from inside the site**, by hand, with a
text editor and `git`. Everything else the full workflow does (semantic
cross-linking, DES scoring, flashcards/quiz, English mirror, learning
pathways, hashtag canonicalization, Pulse, homepage counters) is deliberately
skipped and listed under **Deferred** below. Read **Do not skip** before you
start — three items in the checklist are the actual difference between
"published" and "silently invisible," and it is not obvious from the file
tree which three.

This document does not replace the router. The moment an agent is available
again, run the **Deferred** catch-up pass (or better: hand the page over and
let a full router publish absorb it retroactively).

**Scope note:** this path assumes a normal specialist type — NoteCast,
Insight, Chairside, DentAI, MetaNote, ShareHub, DentCast+, or a core episode.
It does **not** cover **LiteCast** (separate source of truth,
`litecast/lite-glossary.json`, `.ir`-only, no pillar/DES/en-mirror
machinery — its own minimal path would look different) or **glossary terms**
(generated pages, different builder). If your content is one of those, stop
and get an agent, or ask for a variant of this document.

## What "minimal" actually requires (verified against this repo)

The three reachability surfaces you named are genuinely **independent** — the
site's own code confirms this, not just the workflow's prose:

- **Live at its URL** — GitHub Pages serves *any* committed file at its path
  automatically on push to `main` (confirmed: `CNAME` at repo root =
  `dentcast.org`, and `.github/workflows/deploy-arvan.yml`'s own comment
  states outright "`.org` را خودِ GitHub Pages سرو می‌کند"). No build step
  publishes `.org` — committing the `.html` file *is* the publish. **Inferred,
  not confirmed from a file in this repo:** the exact GitHub Pages source
  branch/folder setting lives in repo Settings → Pages, not in a workflow
  file, so I can't read it directly — but a `.github.io`-named repo with a
  `CNAME` at the root deploying from `main` is the standard, near-certain
  configuration.
- **Present in `sitemap.xml`** — generated by `.github/scripts/gen_sitemap.py`,
  which **runs automatically** via `.github/workflows/sitemap_only.yml` on
  every push to `main` (`on: push: branches: ["main"]`, in addition to
  `workflow_dispatch`). You do **not** need to run it or touch `sitemap.xml`
  by hand. It walks every `.html` file in the repo and includes a page **iff**:
  it has a `<link rel="canonical" href="https://dentcast.org/...">` tag, and
  it does **not** have `<meta name="robots" content="...noindex...">`. That's
  the entire test — no brain entry, no builder, no JSON-LD required for
  *inclusion* (JSON-LD `dateModified`/`datePublished` only affects the
  `<lastmod>` value; missing it falls back to git history, which is cosmetic).
- **Linked from an internal surface** — the **cheapest of your three named
  options is the homepage's "LAST 30 UPDATES" widget**
  (`#dcLast3Updates` in `index.html`), and it comes **for free** the moment
  you append a well-formed entry to the tail of `dentcast-brain.json`. Verified
  in `index.html`: that widget does a client-side `fetch('/dentcast-brain.json?v=...', {cache:'no-store'})`
  at runtime, and its `toItem()` function needs only `title` and
  (`page_url`/`url`/`link`) on each entry — nothing else. It sorts by date if
  any entries carry one, otherwise falls back to **array tail order** (`.slice(-30)`)
  — which is exactly Hard Rule 3/4 in the full workflow ("append at the end").
  The homepage rail cards (`.dc-rail-card[data-cat]`, the eight boxes under
  "تازه‌های دنت‌کست") work the same way, keyed on `entry.type`, but **only**
  for eight specific types (`clinical, notecast, meta, chairside, dentai,
  promptologist, sharehub, dentcast_plus`) — not episodes, not photocast, not
  litecast.
  - **The other two named surfaces (type `index.html`, pillar hub) are NOT
    free** — the landing pages (`sharehub/index.html`, `notecast/index.html`,
    etc.) are hand-maintained static `<li>` lists (verified: none of them
    fetch `dentcast-brain.json`), so reaching a reader through one means
    manually editing that HTML file. The pillar hub is **generated** by
    `tools/build_pillar.py all`, a ~2700-line script that also touches
    `glossary/index.html` and every other pillar page — running it by hand
    without the semantic pillar-determination step (2.4) risks nothing being
    literally broken, but it's the heaviest of the three options for zero
    extra reachability once the brain-tail route is already covered.
  - **Trade-off you should know before relying on the brain-tail route
    alone:** it is *temporary*. The "LAST 30 UPDATES" widget only shows the
    last 30 array entries; a rail card only shows the *newest* entry of its
    type. Every subsequent publish (by anyone, any type) pushes your page one
    slot closer to falling off both. The landing-page link, by contrast, is
    permanent once added. This is exactly why it's in **Deferred**, not
    **Do not skip** — but don't mistake "reachable today" for "reachable
    indefinitely" if you never do the catch-up pass.

So the true minimum is: **a correctly-headed HTML file on disk** + **one
well-formed tail entry in `dentcast-brain.json`** + **a push to `main`**.
Nothing else is load-bearing for your three stated criteria.

## Minimum viable brain entry

`dentcast-brain.json` is one flat array (no per-type sections). The **only**
fields the homepage widget's JS actually reads are `type`, `title`, and
`page_url`/`url`. Everything else on an entry (`hashtags`, `keywords`,
`pillar`, `author`, `source`, `caption`, `id`) is metadata that later
automation (search, cross-linking, pathways, DES) depends on — **not** on
your three stated criteria. That said, the file must stay **valid JSON** —
a syntax error here breaks the widget for the **entire site**, every
visitor, not just your new page (see **Do not skip**).

Concrete minimum, modeled on the most recent ShareHub entry (`sharehub-18`,
the simplest schema on the site — no audio, no episode fields):

```json
{
  "type": "sharehub",
  "id": "19",
  "title": "<the exact title, copied — not re-typed>",
  "caption": "<the exact caption, copied — not re-typed>",
  "author": "دنت‌کست",
  "source": "https://dentcast.org",
  "hashtags": [],
  "keywords": [],
  "url": "/sharehub/share-19.html",
  "pillar": {
    "primary": null,
    "secondary": [],
    "subtopic": null
  }
}
```

Notes:
- **`type`, `title`, `page_url`/`url`** — load-bearing for reachability. Not
  optional.
- **`pillar.primary: null`** — legal and verified accepted by
  `verify_publish.py` (`rep.ok("2.4 pillar", "no pillar assigned")`). It just
  means step 2.4's semantic pillar determination is deferred, not faked.
  The `pillar` key and its `subtopic` sub-key must still be **present** even
  when null — the schema-parity check (`Hard Rule 5`) looks for the key set,
  not the values.
- **`hashtags: []` / `keywords: []`** — legal empty arrays. Do **not** invent
  hashtags by hand and write them here; Hard Rule 15 requires resolving them
  against `dentcast-hashtag-reference.json` first, which this path defers.
  An empty array is honest; a hand-typed unvalidated tag is not.
- **Exact key set must otherwise match the most recent same-category entry**
  — this is the schema-parity rule (Hard Rule 5), and it is genuinely
  **type-specific**: episodes carry no `type` key at all; other types carry
  different field sets (e.g. an `audio_url` field for episode/NoteCast).
  **Before writing your entry, find the most recent entry of your chosen type
  and copy its exact key list** — do not use this ShareHub example as a
  literal template for another type. This parity is not required for your
  three narrow criteria, but skipping it silently breaks every later
  automation that assumes uniform per-type shape (see **Deferred**).
- **Append at the absolute end of the array** — not sorted into the middle,
  regardless of type. This is what makes the tail-order fallback work.
- **Episodes are a special case**: an episode entry also needs a matching row
  in `dentcast.json` (duration, audio URL — read by
  `update-homepage-counters.py`'s hour counter and by `build_episodes.py`),
  and reaching `episodes.html` (the landing page) requires running
  `build_episodes.py`. The homepage "LAST 30 UPDATES" widget still works from
  the brain entry alone. If your content is an episode, budget for this extra
  file.

## What `verify_publish.py` will fail on a minimal publish

Run it anyway once you're done — it's useful as a **diff against the full
workflow**, even though you already know it won't be green:

```bash
python3 tools/verify_publish.py <content_id>
```

Expected **FAIL** rows on a page built by this minimal path (for a normal,
non-LiteCast, non-چالش type):

- **`D en-mirror`** — the English mirror at `{type}/en/{file}.html` doesn't
  exist. This is a **hard FAIL**, not a warn, for every type except LiteCast
  and چالش — confirmed in the script (`rep.check(exists(en_rel), ...)` with
  no fallback branch).
- **`4.12 quiz`** — no FAQ entry for this `content_id` in
  `plus/faq-corpus.json` (you didn't author one).
- **`4.11 cards`** — no `DefinedTermSet` block (same reason).
- **`5.6 pathway`** — not placed in any `plus/pathways.json` pathway.
- **`8 plus-index`** — missing from `plus/content-index.json`, **unless**
  you pushed to `main` and let `sitemap_only.yml`'s own
  `build_plus_index.mjs` step self-heal it first (it runs on every push).
- **`8 flashcards`** / **`8 quiz`** — same root cause as `4.11`/`4.12`.
- **`2.5 related`** — no «کاوش بیشتر» section on the page at all (you didn't
  clone/build one) — will read as "found 0 dc-related-section blocks
  (expected 1)" unless your cloned template already had one.
- **`7 version`** — only if you skip `stamp-version.py`; the stamped
  `CACHE_NAME` won't match the freshly-hashed content.
- **`2.6 landing`** — only if you did **not** also do the landing-page edit
  (deferred by default in this path) — it checks the type's `index.html`
  links to the new entry.

Expected **WARN** (not fatal):

- **`4.13 DES`** — "no DES record — confirm this is «بدون DES» or an
  unsourced episode, not a forgotten step 4.13." Correct: you deliberately
  skipped Question 4.8/step 4.13.

Your options, without implementing anything:

1. **Accept a red gate.** Run `verify_publish.py`, read it, keep the output
   as your own record of exactly what's deferred, and move on. This is
   consistent with the mechanical gate's own design — it's meant to *name*
   incompleteness, not force zero incompleteness in every circumstance.
2. **A documented bypass.** None exists today for a partial publish — the
   script has no flag that says "skip these rows." You could manually read
   the FAIL list and cross-reference it against **Deferred** below to confirm
   nothing surprising is failing.
3. **A `--minimal` flag** would need to be *added* to `verify_publish.py` to
   suppress the FAIL→WARN reclassification for the specific rows enumerated
   above (Phase D, 4.11, 4.12, 5.6, 8 plus-index/flashcards/quiz, 2.5, 2.6)
   when explicitly invoked in that mode. This is not implemented here per
   your instruction — flagging it as the natural fix if this path becomes a
   recurring need.

## What breaks or degrades — and what's hard to fix later

**Breaks / degrades while un-caught-up (all recoverable, none of these ships
wrong data — they're absences, not errors):**

- **No English mirror / no fa↔en toggle.** An English-speaking or
  international reader hits a dead end. Recoverable any time by running the
  en-version workflow later — it operates on the existing fa page,
  independent of when it was published.
- **No «کاوش بیشتر» cross-links, no glossary back-link, no in-body
  links.** The page is an island — nothing points to it semantically, and it
  points to nothing. This is the single biggest SEO/topical-authority cost
  given how much this site's link architecture is described in `CLAUDE.md`
  (pillar structure, glossary back-linking, cross-link sweeps). Recoverable
  later, but until the catch-up runs, the page contributes zero internal
  link equity in either direction.
- **No pillar/subtopic assignment.** The page is invisible on its
  `/pillar/<slug>/` page and its premium `structure.json` sidecar, and won't
  appear correctly in the "میز کار" dashboard's subject tree even after
  `build_plus_index.mjs` picks it up generically. Recoverable — step 2.4 can
  run retroactively.
- **No DES (evidence score) record.** No evidence-basis badge on the page.
  Recoverable, but note the workflow's own philosophy here: a page that
  *should* carry a science-based score and doesn't yet is a **pending**
  state, not silently wrong — there is no fallback that scores it
  incorrectly by default.
- **No flashcards / quiz questions.** The page contributes nothing to the
  Leitner flashcard deck or the scored quiz bank. Recoverable.
- **No hashtag canonicalization.** If you did write hashtags by hand instead
  of leaving `[]`, they will not be validated against
  `dentcast-hashtag-reference.json` and won't be searchable via the AI
  case-assistant (which reads the canonical vocabulary, not raw brain
  strings). **This is a case where recovery costs more the longer you wait**:
  every additional hand-typed, unvalidated hashtag elsewhere compounds the
  cleanup. Recommendation: leave `hashtags: []` rather than guess.
- **Stale `plus/content-index.json` / `plus/pathways.json` / dashboard nav.**
  Self-heals partially (content-index, via `sitemap_only.yml`'s own build
  step on every push) but pathways do not self-heal — they need step 5.6 run
  explicitly.
- **No `dc-notify` publish marker (Phase E).** No push notification fires to
  subscribed readers. If you add the marker later and push again, the
  `notify-new-articles` Action's `content_id`-dedup logic (keyed off the
  canonical URL, not the file) will still fire it correctly whenever it first
  sees the marker — so this is fully recoverable, just delayed.
- **Homepage counters and static SEO fallback text stay stale** until
  `update-homepage-counters.py` runs. Cosmetic only (real content is fetched
  live).

**Nothing in this list becomes structurally hard to fix by having been
skipped at publish time** — the site's design (brain as source of truth,
generated indexes, idempotent injectors) means every deferred item is a
later, independent, replayable step. The **one genuine risk that is not
"pending" but actively harmful if done wrong** is described in **Do not
skip** below.

## `.ir` deploy (dentcast.ir) — explicit manual step

`.github/workflows/deploy-arvan.yml` is **`workflow_dispatch`-only** — it
does **not** fire on push to `main`. Per its own comment: it is "the only
thing that builds `dentcast.ir`" (`.org` is GitHub Pages, automatic on
push). Practically:

1. Push your changes to `main` as normal (this updates `.org` automatically
   and triggers `sitemap_only.yml`, which regenerates **both**
   `sitemap.xml` (`.org`) and `sitemap-ir.xml` (`.ir`) — the sitemap
   generator itself needs no manual trigger for either domain).
2. To make the page reachable at **`dentcast.ir`**, go to the repo's
   **Actions** tab → **"Deploy DentCast to Arvan Object Storage"** →
   **"Run workflow"** → select `main` → Run. This syncs the entire working
   tree to Arvan object storage via `aws s3 sync --delete` and then forces
   cache revalidation on a specific list of cache-sensitive files
   (`dc-nav.js`, `spot/spot.js`, `spot/spot-config.json`, and everything
   under `plus/`).
3. **This is a real, repo-wide sync**, not an incremental publish of just
   your page — `--delete` means anything removed from the working tree since
   the last Arvan sync is also removed from the bucket. If other changes are
   mid-flight on `main` from unrelated work, they ship to `.ir` too at the
   same time. This is a normal characteristic of the existing pipeline, not
   something this minimal path introduces — but it's worth knowing before
   you click Run.
4. There is no cron/webhook re-triggering this automatically — if you forget
   step 2, `.ir` silently serves the pre-publish version indefinitely, with
   **no red CI run to notice** (this exact failure mode is what the
   Persian comment in `deploy-arvan.yml` documents having happened twice on
   2026-08-06).
5. **Caveat inherited from the same file's own reasoning, worth knowing but
   not actionable here**: a PR merged via GitHub's API (rather than the web
   UI's merge button, or a direct `git push`) can fail to emit a real `push`
   event, which is why `deploy-arvan.yml` needs its manual-dispatch fallback
   in the first place. The same risk theoretically applies to
   `sitemap_only.yml`'s `push` trigger. If you push directly with
   `git push origin main` (as this whole document assumes), you're using the
   reliable path and this caveat doesn't apply to you.

## The minimal path — numbered checklist

Assumes: a normal specialist type (not LiteCast, not a چالش), a text editor,
and `git`. Work on a branch, then push to `main` (or open a PR and merge it
normally — not via API automation, see the caveat above).

1. **Pick the type and find your two templates.** In `dentcast-brain.json`,
   find the **last** entry whose `type` matches your content (or, for
   episodes, the last entry with **no** `type` key). Note its exact key set
   and its `url`/`page_url` value — that tells you the on-disk template page
   to clone (e.g. `sharehub/share-18.html` → your new page is
   `sharehub/share-19.html`).

2. **Copy the template HTML file to the new filename**, then hand-edit only:
   - `<title>`, `<h1>`, meta `description`, `og:title`, `og:description`,
     `twitter:title`, `twitter:description` — new content.
   - `<link rel="canonical" href="https://dentcast.org/{new-path}">` — the
     domain **must stay `dentcast.org`** (never `.ir` for a non-LiteCast
     type); only the path changes.
   - JSON-LD: `headline` → new title; `datePublished` and `dateModified` →
     today, and **identical to each other**.
   - Body text (the actual content).
   - Any media `src`/`data-src` (image, audio) from what you were given.
   - **Verify, don't add:** the GA4 snippet (`G-GMM0WC8X3M`, appears twice —
     once in the `gtag('config', ...)` call, once in the script `src`), the
     two `<link rel="preconnect" ...>` tags (`api.dentcast.ir` and
     `api.dentcast.org`, both), and the 3-line hreflang block
     (`fa` / `fa-IR` / `x-default`) all **survived the copy unchanged** —
     they came from the template and must not be edited or dropped.
   - **Delete or leave inert** the «کاوش بیشتر» `dc-related-section` block if
     present in the template (you're deferring pillar/glossary linking —
     leaving a stale capsule pointing at the *previous* article's context
     would be worse than removing it). If the template has one, either
     delete the block entirely or leave it truly empty — do not leave it
     pointing at the wrong pillar.
   - **Write a real opening paragraph before any list**, if your body has
     one — this isn't cosmetic, it's where the site's ad-slot logic looks
     for an insertion point; a list-only body pushes the ad to the very end
     regardless of platform automation.

3. **Append the brain entry.** Open `dentcast-brain.json`, go to the very
   end of the array, and add your new object (see the concrete example
   above) as the **last** element — after the current last element, with a
   comma before it, no comma after. **Validate the JSON before saving** —
   see **Do not skip**, item 1.

4. **(Episodes only)** add the matching row to `dentcast.json` (duration,
   audio URL) if your content is a core episode.

5. **(Optional but recommended for durability, not required for today's
   reachability)** Manually add one `<li><a href="{file}.html">{title}</a></li>`
   line at the **top** of the list in your type's `{type}/index.html`
   (matching the exact markup pattern of the existing list items — see e.g.
   `sharehub/index.html`'s list for the pattern). This is what makes the page
   reachable **permanently**, not just until it ages off the homepage's
   last-30 window.

6. **(Recommended, cheap)** Run `python tools/stamp-version.py` from the repo
   root. No dependencies, standard library only, safe to run even though
   you're skipping the other builders.

7. **Commit and push to `main`** (`git add`, `git commit`, `git push origin
   main`, or a PR merged through the normal web UI). This alone:
   - Publishes the page live via GitHub Pages (`.org`).
   - Triggers `sitemap_only.yml`, which regenerates `sitemap.xml`,
     `sitemap-ir.xml`, and `plus/content-index.json`, and commits them back
     automatically. **No manual sitemap step is needed.**

8. **Verify reachability, three separate checks:**
   - Open `https://dentcast.org/{your-path}.html` directly — confirms
     "live."
   - After `sitemap_only.yml` finishes (check the Actions tab), open
     `https://dentcast.org/sitemap.xml` and confirm your URL is listed —
     confirms "indexable."
   - Open `https://dentcast.org/` and confirm your title appears in the
     "تازه‌های اخیر" / last-updates list (or its rail card, if your type is
     one of the eight rail categories) — confirms "reachable."

9. **(For `.ir` reachability)** go to Actions → "Deploy DentCast to Arvan
   Object Storage" → Run workflow on `main`, per the `.ir` section above.

10. **Run the gate for your own record, expect it red, read it against the
    Deferred list below to confirm nothing unexpected is failing:**
    ```bash
    python3 tools/verify_publish.py {content_id}
    ```

## Do not skip

Three things in this checklist are not "best practice," they are the actual
difference between a successful minimal publish and a silent, undetected
failure:

1. **`dentcast-brain.json` must remain valid JSON after your edit.** This
   file is fetched client-side, unparsed as-is, by every visitor's browser on
   every homepage load (the "LAST 30 UPDATES" widget, the rail cards, the
   quick-look cards) — and it's the taxonomy source for
   `build_plus_index.mjs`, which runs automatically on every push via
   `sitemap_only.yml`. A trailing-comma or bracket mistake here doesn't just
   fail to add *your* page — it can break the widget (and, if the pillar/
   plus-index builders choke on it downstream) for **the entire site**, for
   every visitor, silently (a `fetch().catch(() => {})` swallows the error in
   the widget's own code — you'll see nothing in the browser, just an empty
   list). **Validate before committing:**
   `python3 -c "import json; json.load(open('dentcast-brain.json'))"` — if
   this doesn't error, the JSON is syntactically sound.

2. **The entry must be the last element of the array, appended, never
   inserted mid-list.** This is what the tail-order fallback in the homepage
   widget's JS depends on when no entries carry parseable dates in a
   consistent way it can sort by, and it's Hard Rule 3/4 of the full
   workflow for the same underlying reason. Insert it anywhere else and
   "reachable from the homepage" quietly stops being true, with the entry
   still sitting in the file, looking published.

3. **The canonical tag must read exactly `https://dentcast.org/{path}.html`
   and the page must carry no `noindex` robots meta.** `gen_sitemap.py`'s
   inclusion test is exactly and only these two conditions — get either
   wrong (clone carries a stray `noindex`, or you fat-finger the canonical
   path) and the page is live and browsable, brain-linked, everything looks
   done — but it will never appear in `sitemap.xml`, and Google will never
   be told it exists. Nothing on the page itself will look wrong to you when
   you check it in a browser; this is the failure mode most likely to go
   unnoticed without deliberately opening `sitemap.xml` and searching for
   the URL, which is why step 8 of the checklist makes that its own explicit
   check rather than folding it into "does the page load."

Everything else in the deferred list is a **pending** state — visibly
incomplete if you look, recoverable at any time, and not silently wrong.
These three are the ones that can make a "successful" minimal publish
actually fail one of your three stated goals without you knowing it did.
