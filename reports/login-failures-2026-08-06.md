## یافتهٔ ۱ — علتِ اصلیِ «نمی‌توانم وارد شوم» (بحرانی)

### مکانیزم

سه چیز که هر کدام جداگانه درست‌اند، کنار هم یک باگ می‌سازند:

**الف) کلاینت دو میزبان API دارد و بی‌صدا بینشان جابه‌جا می‌شود.**
`plus/js/config.js:20-21`

```js
if (h.indexOf('dentcast.org') !== -1) return ['https://api.dentcast.org', 'https://api.dentcast.ir'];
return ['https://api.dentcast.ir', 'https://api.dentcast.org'];
```

**ب) کوکیِ نشست host-only است.** `plus-api/src/services/session.ts:22-31` هیچ
`domain` نمی‌دهد. یعنی کوکی‌ای که `api.dentcast.ir` ست کرده، هرگز به
`api.dentcast.org` فرستاده نمی‌شود — حتی با اینکه هر دو به همان کانتینر می‌روند.
مرورگر بر اساس هاست تفکیک می‌کند، نه بر اساس اینکه پشتش چه کسی است.

**ج) از ۱۳ مرداد، ۱٫۵ ثانیه کندی کافی است تا جابه‌جا شود.**
`plus/js/api.js:41` (کامیت `54180cf`):

```js
const PROBE_TIMEOUT_MS = 1500;
```

پیش از آن کامیت، فیل‌اوور فقط با خطای واقعی شبکه رخ می‌داد؛ یعنی عملاً میزبانِ
اولِ خودی تقریباً همیشه برنده بود. حالا اگر `/health` میزبانِ خودی در ۱۵۰۰
میلی‌ثانیه جواب ندهد، کلاینت **بی‌هیچ پیامی** می‌رود سراغ میزبانِ دیگر.

### نتیجه برای کاربر

۱. کاربر لاگین است. کوکی روی `api.dentcast.ir` نشسته.
۲. کانتینر API یک لحظه کند می‌شود (ری‌دیپلوی، رولینگ ری‌استارت، یا شبکهٔ موبایل).
۳. تبِ بعدی که باز می‌کند، پروب `/health` تایم‌اوت می‌کند → `resolvedBase` می‌شود
   `https://api.dentcast.org`.
۴. `GET /me` به آن میزبان می‌رود **بدون کوکی** → `401` → هدر آیکونِ مهمان نشان
   می‌دهد. کاربر: «من که لاگین بودم، پریدم بیرون.»
۵. دوباره وارد می‌شود. کد OTP را می‌زند. موفق. ولی کوکی این بار روی
   `api.dentcast.org` می‌نشیند.
۶. صفحهٔ بعد، `api.dentcast.ir` سالم شده → پایه برمی‌گردد به آن → باز `401`.
   **پینگ‌پونگ.** «هرچه می‌زنم نمی‌رود تو.»

نکتهٔ مهم: `resolvedBase` در `sessionStorage` کش می‌شود و `sessionStorage` per-tab
است؛ پس همان تب پایدار می‌ماند و تبِ بعدی دوباره پروب می‌کند. دقیقاً همین است که
باعث می‌شود گزارش‌ها «قاطی» به نظر برسند: برای بعضی کار می‌کند، برای بعضی نه، و
برای یک نفر یک بار می‌شود و یک بار نمی‌شود.

### چرا «امروز»

`plus-api` امروز عوض شده (`08e9337` — تسویهٔ پرداختِ برنگشته) و پیش از آن هم
`b6740a4`/`87896e9`. هر ری‌دیپلویِ کانتینر یک پنجرهٔ چندده‌ثانیه‌ای می‌سازد که
`/health` کند یا قطع است — و در آن پنجره **هر کسی که یک تب تازه باز کند** بی‌صدا
به میزبانِ اشتباه سوییچ می‌شود و نشستش را از دست می‌دهد.

> نتوانستم از این سندباکس به `api.dentcast.ir` و `api.dentcast.org` وصل شوم
> (پراکسیِ محیط با ۴۰۳ رد می‌کند)، پس نتوانستم *تأیید* کنم که امروز واقعاً کند
> بوده. ولی مکانیزم بالا کاملاً از روی کد قابل اثبات است و دقیقاً همان الگوی
> «بعضی‌ها، امروز» را تولید می‌کند.

### رفع پیشنهادی (به ترتیب اولویت)

1. **پایه را بعد از ورود قفل کن.** لحظه‌ای که یک ورود موفق کوکی می‌گیرد، همان
   میزبان باید در `localStorage` (نه `sessionStorage`) بنشیند و فیل‌اوور دیگر
   حق نداشته باشد آن را عوض کند تا وقتی که یک خطای شبکهٔ واقعی بدهد.
2. **یا** فیل‌اوور را فقط برای درخواست‌های بدونِ نشست مجاز کن؛ هر مسیرِ `auth`
   و `/me` همیشه روی میزبانِ خودیِ سایت بماند (همان قاعده‌ای که در کامنت
   `defaultBases()` نوشته شده ولی در `pickBase()` رعایت نمی‌شود).
3. **یا** `PROBE_TIMEOUT_MS` را برای میزبانِ **خودی** برداشته/خیلی بلند کن و فقط
   برای میزبانِ دوم نگه دار — ۱٫۵ ثانیه برای یک کانتینر در حال ری‌استارت خیلی کم
   است.

گزینهٔ ۱ و ۲ با هم درست‌ترین‌اند. تغییرِ `domain=.dentcast.ir` روی کوکی مشکل را
حل **نمی‌کند**، چون دو دامنهٔ سطح‌بالا (`.ir` و `.org`) در هر حال جدا می‌مانند.

## یافتهٔ ۲ — «به تلگرام وصل نمی‌شود» (بالا)

### مکانیزم

`CNAME` این ریپو `dentcast.org` است، یعنی سایتِ اصلی روی `.org` سرو می‌شود. و:

`plus/js/config.js:129-132`
```js
export function telegramLoginEnabled() {
  if (OVERRIDE.forceTelegramLogin) return true;
  return location.hostname.indexOf('dentcast.org') !== -1;
}
```

پس دکمهٔ تلگرام **فقط روی `.org` روشن است** — و مخاطبِ `.org` هم همان دندان‌پزشکِ
داخل ایران است. کامنتِ بالای همین تابع خودش دلیل را نوشته:

> «Telegram is filtered in Iran and the widget loads from telegram.org /
> oauth.telegram.org, so the button would be broken for non-VPN users»

این دلیل برای خاموش‌کردنِ دکمه روی `.ir` استفاده شده، ولی روی `.org` — که دامنهٔ
اصلی است — دکمه روشن مانده.

### آنچه کاربر می‌بیند

`plus/js/login-modal.js:146-170` اسکریپت ویجت را بدون هیچ `onerror` تزریق می‌کند:

```js
s.src = 'https://telegram.org/js/telegram-widget.js?22';
```

- **بدون VPN:** `telegram.org` فیلتر است. درخواست بلک‌هول می‌شود (نه ریست سریع)،
  پس مدت‌ها معلق می‌ماند و بعد بی‌صدا می‌میرد. `.dcp-tg-holder` در
  `plus/plus.css:814` `min-height: 40px` دارد → کاربر یک **کادرِ خالیِ ۴۰ پیکسلی**
  زیر عنوان «ورود سریع با تلگرام» می‌بیند. نه دکمه‌ای، نه خطایی، نه توضیحی.
- **بدتر:** اگر اسکریپت از کش بیاید یا VPN قطع‌ووصل شود، دکمه رندر می‌شود و کلیک
  روی آن کلِ تب را به `oauth.telegram.org` می‌برد — که فیلتر است. کاربر از سایت
  بیرون پرت می‌شود روی یک صفحهٔ سفیدِ معلق. **دقیقاً «یک مدت رویش می‌زنند،
  نمی‌رود تو».**
- متنِ زیرِ عنوانِ مودال هم روی `.org` عوض می‌شود به «با تلگرام وارد شوید، یا از
  شماره موبایل استفاده کنید» (`login-modal.js:209`) — یعنی سایت فعالانه کاربر را
  به سمت راهی می‌فرستد که برایش کار نمی‌کند.

### سه سطحِ درگیر

1. مودال ورود — `plus/js/login-modal.js:146`
2. صفحهٔ پروفایل، ردیف «تلگرام» — `plus/js/profile.js:394-406`
3. کارتِ خوش‌آمدِ مهمان که می‌نویسد «با موبایل یا تلگرام وارد شو» —
   `plus/js/welcome.js:52-54`

### رفع پیشنهادی

ساده‌ترین و درست‌ترین کار: `telegramLoginEnabled()` را روی `.org` هم `false` کن
(همان کاری که برای `.ir` شده). زیرساختِ بک‌اند (دو توکن، `verifyTelegramAuthAny`،
کالبک) دست‌نخورده می‌ماند و هر وقت شرایط عوض شد با یک خط برمی‌گردد.

اگر می‌خواهی دکمه بماند: حداقل یک `s.onerror` + تایم‌اوت بگذار که بعد از ~۳ ثانیه
کادرِ خالی را با یک جملهٔ صریح جایگزین کند («ورود با تلگرام در حال حاضر در دسترس
نیست؛ با شماره موبایل وارد شوید») — تا کاربر منتظرِ چیزی که نمی‌آید نماند.

**تصمیمِ محصولی است، نه فنی — پس اعمالش نکردم.** ببین کدام را می‌خواهی (یافتهٔ ۳
را هم پیش از تصمیم بخوان).

## یافتهٔ ۳ — حساب‌های فقط-تلگرامی قفل‌اند (بالا)

در `plus-api/src/routes/auth.ts:371-385`، حالتِ (C) کالبکِ تلگرام یک پروفایل با
`phone = null` می‌سازد. آن حساب **هیچ راه ورودِ دیگری ندارد**.

راهِ وصل‌کردنِ شماره (`POST /auth/phone/link`) خودش `loadUser(request)` می‌خواهد
— یعنی باید *اول وارد شده باشی*. پس هر کسی که حسابش را با تلگرام ساخته و الان
بدون VPN است، عملاً به حسابش (استریک، هایلایت‌ها، اشتراک) دسترسی ندارد و راهِ
خودخدماتی هم برایش وجود ندارد.

اگر دکمهٔ تلگرام خاموش شود، این افراد باید دستی نجات داده شوند (وصل‌کردن شماره به
پروفایلشان از سمت ادمین). تعدادشان را نمی‌دانم — به DB دسترسی ندارم؛ با یک
`select count(*) from profiles where phone is null and telegram_id is not null`
معلوم می‌شود.
