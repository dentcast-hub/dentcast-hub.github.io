# DentCast Repo — Publishing Protocol

> **Agent parity — read before acting.** This repo is worked on by more than one
> agent (Claude Code, Cursor, Codex/GPT). The behavioral contract that makes
> their output identical — conversation language, which confirmation gates are
> never automatic, what to do when a capability (web search, Google Drive,
> ffprobe) is missing, the deterministic hash/build/validate commands, the
> output-parity checklist, and the git protocol — lives in
> **`.dentcast/workflows/agent-parity.md`**. `AGENTS.md` at the repo root is the
> agent-neutral mirror of this file, and `.cursor/rules/*.mdc` are Cursor's
> routers into the same canonical workflows.
>
> **Maintenance rule:** if you change a trigger, a rule, or a section here, make
> the same change to `AGENTS.md` and `.cursor/rules/dentcast-router.mdc` **in the
> same commit**. Logic lives in the canonical workflow files; routers only point
> at them; behavior lives in `agent-parity.md`. None of them duplicates another.

This repo powers DentCast. When the user brings new content to publish:

1. Read `.dentcast/workflows/README.md` and follow it strictly.
2. `dentcast-brain.json` is the source of truth for every content type's structure, schema, and category. Always use the most recent entry of the SAME category as the template for any new entry.
3. Never mix categories. NoteCast stays in NoteCast. Insight stays in Insight. Each category's entries go to their own section/array in the brain and their own directory on disk.
4. The "latest content" widget on the homepage reads the LAST entries from `dentcast-brain.json`. Therefore, every new entry MUST be appended at the END of its category in the brain — never inserted mid-list.
5. Auto-discover whatever you can. Ask the user only for things you genuinely cannot determine.
6. Brain entry schema is sacred. Never add new fields to a brain entry that don't exist on previous same-category entries. Match the existing shape exactly.
7. A string the user supplied is **copied, not re-typed** (Hard Rule 16). A ZWNJ (`U+200C`) is not a space — «اندو‌شده» ≠ «اندو شده» — and widening their caption by a clause is a rewrite, not a copy. Propose changes; never make them in passing.
8. Correcting a title or caption after the fact is a **sweep, not a spot edit** (Hard Rule 17). A title lives on ~8 surfaces and a caption on ~4 (including the en mirror); all of them change in the same commit, then the builders re-run.
9. **A publish ends with a green gate, not with a claim.** After Phase E, run Phase F and paste its summary line into the report:
   ```bash
   python3 tools/verify_publish.py <content_id> \
     --expect-title "<title exactly as the user wrote it>" \
     --expect-caption "<caption exactly as the user wrote it>"
   ```
   Non-zero exit = the publish is incomplete. Every `FAIL` row prints its own fix command. The gate does not replace any step — it catches what a long checklist forgets (a builder run out of order, a surface a correction missed, an invisible character that changed).
10. **Every publish is scored — DES runs the prompt file, and a DOI is never guessed.** Phase B **Question 4.8** sorts the publish into one of three baskets and Phase C **step 4.13** does the work: load `.dentcast/dentcast-evidence-score-v2.4.md` as the system prompt (whole file, minus its appendix — that appendix is the pipeline contract you run yourself), one input block **per cited source**, then store the output verbatim in `plus/des-scores.json`. **The scoring model never fetches**, so `source_text` must be resolved *before* the prompt runs — local cabinet first, then PubMed MCP, then WebFetch — and a source whose abstract you could not retrieve ends as `INSUFFICIENT_TEXT`, never as a score assembled from the DentCast متن about it. **The content TYPE never picks the track — what the page CITES does.** A page carrying a retrievable identifier (a DOI, a `doi.org` link, a PubMed id, a «منابع» block) is basket 2 and gets **one record per cited source**, whatever section it lives in; a page whose متن is the author's own reasoning with no such identifier is basket 1 (COMMENTARY). `sharehub/` is what forced this: eight of its pages are short practical notes with no citation at all, while `share-11` stands on **eleven** DOIs and `share-14` on **twelve**, and the old "ShareHub is COMMENTARY by definition" rule would have scored the founder's transparency on a page whose real basis is a dozen published studies. Naming a study in prose without an identifier is neither — `metanotes/meta-14` quotes one figure from «مطالعه Morimoto» and argues from it under its own heading, so it is a write-up of the analysis, not of the review, and scores COMMENTARY. The third basket is the one that always stops: research-shaped content with **no identified paper** (an episode with only a caption and audio) is asked as two named options — «DOI می‌دم» or «بدون DES منتشر بشه» — and there is no third answer, in particular not scoring it as COMMENTARY to have something. Skips are LiteCast and the user's own «بدون DES»; both are reported, never silent. **The COMMENTARY track has one closed carve-out (v1.6, widened in v1.7):** checklist item 4 («صریحاً تجربه/دیدگاه نامیده شده») may be earned from the *section's own published declaration* instead of a sentence inside the page — for `chairside/`, `metanotes/` and `insight/` only, whose landing pages carry one and which the spec quotes verbatim in a closed table. The `evidence_quote` is then that declaration copied verbatim from the landing page, and the item's `note` is mandatory and names that file. The list is closed and there is exactly one way in, which `insight/` is the precedent for: **the section's landing page gets an explicit declaration first, and the spec version bumps after** — never because a section resembles one already listed. `insight/` did not qualify under v1.6, when its page said the series covers «تجربه‌های بالینی **و** یافته‌های علمی» and so could not tell a reader which of the two the page in front of them was; it qualifies under v1.7 because that page was rewritten, not because the section was reconsidered.

## English-version protocol (trigger)

There is a **second** workflow alongside the publishing router. When the user
asks to produce the **English (en) version of an existing page** — trigger
phrase **«… رو انگلیسی کن»** (e.g. «پرامپتولوژیست ۱ رو انگلیسی کن»,
«نسخه‌ی انگلیسیِ متانوت ۳») — do **not** use the «متن جدید دارم» publishing
router. Instead read `.dentcast/workflows/en-version.md` and follow it
strictly. That workflow mirrors one existing page into
`/{type}/en/{same-filename}.html`: English chrome cloned from
`metanotes/en/meta-1.html`, body/schema inherited and translated from the
source's own type, and a real per-document fa↔en toggle on both sides. en
pages are standalone translations AND a reader-only surface: they ship
**noindexed** (`noindex, follow`, zero hreflang, out of the sitemap — they
are unreviewed AI translations; 2026-08-11 SEO audit) and get **no**
`dentcast-brain.json` entry, **no** Pulse line, and **no** specialist
cross-linking.

**Note — the publishing router already invokes this workflow automatically.**
Every normal `.org` publish ends with **Phase D** of
`.dentcast/workflows/README.md`, which runs this same en-version workflow on
the page it just published — so a freshly published page **always** ships with
its English mirror + a working fa↔en language toggle (Hard Rule 12), never a
toggle-less page. The **«… رو انگلیسی کن»** trigger therefore remains for
mirroring an **older/pre-existing** page that predates that rule (or any page
whose en version is missing) — it is the on-demand entry point to the *same*
machinery the router now calls on its own. **Two exceptions, and no others:**
LiteCast is `.ir`-only with no hreflang, so it gets no en mirror or toggle in
either path; and a **چالش** refuses this trigger for a mechanical reason
(`.dentcast/challenge-handoff.md` RULE 16) — its en mirror would be a
*different* `content_id` with no row in the `challenges` table, so the toggle
would lead to a page missing the only thing on it. Neither gets an en mirror
or toggle in either path.

## Ad-publishing protocol (trigger)

There is a **third** workflow alongside the publishing router and the
en-version router. When the user says they have an **advertisement** to
publish or manage — trigger phrases like **«تبلیغ دارم»**, «آگهی دارم»,
«اسپانسر گرفتیم», «تبلیغ X رو خاموش کن», «سهم اسپانسر رو کم/زیاد کن» — do
**not** use the «متن جدید دارم» publishing router. Instead read
`.dentcast/workflows/ads.md` and follow it strictly. An ad is not content:
it gets **no** page, **no** brain entry, **no** Pulse line, **no** en mirror
— the whole ad system lives in `spot/spot-config.json` (see `spot/README.md`).
That workflow interviews for the gaps (sponsor vs internal, link, copy,
image, slots, rotation share) and files sponsors so they automatically ship
with `rel="sponsored"` (Google compliance). Never hardcode an ad into a page.
**Always ask which of the four زمان‌ها (rotation beats) the new ad takes and
what fills the rest** — the rotation advances once per **ad-showing page
view**, so a four-entry `rotation.sequence` = four page views (four refreshes,
or four articles, is one full lap), and an ad assigned to no beat renders never
(ads.md hard rule 6 + Phase B question 6).

## Ad-reporting protocol (trigger)

When the user asks for **ad numbers** — «گزارش تبلیغ بده», «آمار تبلیغات»,
«تبلیغ‌ها ماه گذشته چقدر دیده شدن؟», «کلیک اسپانسر X چقدر بوده؟» — read
`.dentcast/workflows/spot-report.md` and follow it. This is read-only: no
config edit, no publish. Every ad render/click already reports to **our own
API** (`spot_impression`/`spot_click` → aggregate counters, read back via
`GET /admin/spot/stats` — or, already formatted, the **«گزارش تبلیغ‌ها»** section
of the `GET /admin` page, with its three windows ۲۴ ساعت/۷ روز/۳۰ روز and each
تبلیغ broken down by محل) **and** to GA4 as a cross-check, so the report is a
lookup, not a build. **«۲۴ ساعت» there is the Tehran calendar day, never a
rolling window** — `spot_stats` is keyed by day and carries no hour, so a real
last-24-hours figure does not exist in this data and must not be implied. Our API is the source of truth: adblockers drop GA but
not a same-site subdomain. Three rules that decide whether the answer is
right: the headline number is always **تعداد بارِ نمایش** (one person seeing
an ad 20 times is 20 — there is deliberately no per-user attribution, so
"چند نفر" is unanswerable), **premium is zero by design, not by
measurement**, and no data of any kind exists before 2026-07-26. Numbers are
never guessed — if the data isn't in hand, hand over the command instead.

## Cross-link protocol (trigger)

A **fifth** workflow. When the user asks to point **existing** article bodies at
a **newly published glossary term** — trigger phrases like **«کراس‌لینک بزن»**,
«بک‌لینک دانشنامه», «واژه‌های جدید رو به متن‌های قدیمی وصل کن», and in practice
after publishing a batch of terms — read `.dentcast/workflows/cross-link.md` and
follow it. **It has two entry points and one machine, the same split
`en-version.md` uses:** every **glossary** publish ends by running it *scoped to
the term it just published* (publishing-workflow **step 4.7-ب**, `--slug <new
slug>`), because a term must not be born with zero inbound links; and the
**unscoped** backlog sweep is the on-demand trigger above. A publish of any other
type skips it — its subject is a page, not a term. It exists because the
publishing router links **forward only**: step
4.8 runs on the page in flight and points it OUT at terms that already exist, and
4.7 (the one inbound step) reads only `glossary/glossary.json` and writes only
into the «کاوش بیشتر» section, never into prose. So a term's inbound in-body link
count is a function of how much content was published *after* it — a foundational
term born today starts at zero and stays there. **Scope is what makes it safe inside a publish, not staying out of one**:
scoped, it is bounded and no different in kind from step 4.7, which already edits
other pages mid-publish; the **unscoped** sweep opens every page in the corpus,
which no publish gate can verify, so that one keeps its own invocation and its
own commit.
The mechanical half is two tools — `tools/cross_link_candidates.py` (read-only
proposal generator) and `tools/cross_link_apply.py` (**the only writer**, which
verifies each file's rendered text before writing it and refuses the file if it
would change) — and neither is to be re-derived in prose — a whole-document scan
instead of the per-type body boxes produced 74 false positives on the first run.
Four rules the whole thing rests on: **anchors only, text never changes** (gated
by stripping every tag and comparing the rendered string byte-for-byte, because
those paragraphs are the founder's own words — Hard Rule 16); **the signal is the
page's own hashtags + `keywords`**, resolved through the hashtag reference's alias
layer, never a site-wide string scan; **a ZWNJ is not a word boundary**, so
«ایمپلنت» inside «ایمپلنت‌محور» or «ایمپلنتی» is never wrapped (15 of the first
run's 85 candidates, all invisible in a plain diff); and the density ceiling is
the site's **measured p90 of 12 in-body links per 1000 words**, not an invented
number. `episodes/` is out of scope — its body is the «درباره این اپیزود»
caption, median 13 words, where one link is ~77 per 1000 — alongside LiteCast, en
mirrors and the glossary's own pages. The **first** unscoped sweep over the
107-term backlog has its own spent-when-done brief,
`.dentcast/glossary-crosslink-sweep-handoff.md`. Nothing outside the touched pages changes:
no brain write, no builder, and **no version bump** (article pages are not in
`stamp-version.py`'s content hash — confirm it reports *unchanged*).

## New-section protocol (trigger)

A **sixth** workflow. When the user wants to create a **new content section** —
a new root folder with its own landing page and its own brain `type` («یه بخش
جدید می‌خوام», «پلاک صفر رو راه بنداز», «یه سکشن تازه بساز») — or a **new
pillar**, read `.dentcast/workflows/new-section.md` and follow it. Publishing a
**part into an existing section** is the ordinary router
(`.dentcast/workflows/README.md`), not this file.

It exists because the list of generators that must learn about a new section was
written down nowhere and had to be rediscovered by reading the tree — which is
exactly what **پرامپتولوژیست** paid for. Published under `/dentai/promptologist/`
and registered in five navigation surfaces, it was never registered in the places
that decide what a section *is*: no pillar (so its 19 parts were filed
`digital`/`ai`, where they were **half the entire digital pillar** and 19 of the
23 items in its هوشِ مصنوعی subtopic); no key in `build_pillar.py`'s two type
maps (so `detect_type()` fell through to the `/dentai/` URL prefix and every row
on the topical index rendered as **«دنت‌AI»**); no `FOLDER_META` entry, and a
`countArticles()` that assumed key == top folder (so 19 pages counted **zero**
and the section was absent from the Plus dashboard tree); a `get_priority()` 0.9
rule anchored on one path segment (so its landing page scored **0.7**, alone
among every section landing page); and no row in `inject_hub_og.py`'s `HUBS` (so
that landing page carried **zero** Open Graph tags and produced no share card).
None of it was visible from the section's own folder.

Three rules the checklist rests on. **Register at section creation; surface at
first publish** — the homepage category cell, the rail card, the Pulse line and
the desktop tree item all render a section's *content*, so shipping them empty
announces that there is none; everything inert (type maps, folder maps, colours,
sitemap rules, `global-search.js`) is safe to land immediately. **`--bump` runs
last** — `build_pillar.py`'s `asset_v()` reads `.dentcast/asset-versions.json`
and raises rather than guessing, so the content builders run first and
`tools/asset_version.py --bump` closes the sequence. And **the canonical set is
the gate**: `content_id` comes from each page's `<link rel="canonical">`
(`plus/js/config.js` `detectContentId()`) and is the join key for
`content_votes`, `highlights`, `article_notes`, `support_tickets`,
`collection_items` and `user_activity` — so a canonical that changed on an
existing page has silently rewritten that page's identity across nine tables.
Diff the full canonical set before and after; the only legal difference is
ADDITIONS — the new section's own pages, plus `/pillar/<slug>/` when a pillar
was created in the same task. If one moved or vanished, stop.

**Three of the build steps reach outside the section you are adding, and the
2026-09-07 run is the measurement:** `build_pillar.py all` rebuilds
`glossary/index.html` too; `inject_hub_og.py` runs over every hub, and fixed
five *unrelated* landing pages (chairside, dentai, dentcast-plus, insight,
notecast) that had been shipping with no Open Graph tags at all — additive,
idempotent, no canonical touched, but capture the hashes and report it;
and `asset_version.py --bump` swept **864 pages and 12 assets**, `dc-nav.js`'s
`var V` and the shared module-import stamp included. `gen_sitemap.py` is the
one build step to leave alone from a shallow clone — its `lastmod` fallback
needs full git history and CI owns it.

**No new section is ever nested.** `/dentai/promptologist/` is the site's one
two-level content path and is kept only because its canonicals are load-bearing;
that exception is expressed once, in `tools/build_upboard_index.py`'s
`folder_of()`, and is never to be copied.

## Attached paper file (trigger — ANY type, file-driven)

The paper actions are triggered by the **paper file itself**, *not* by the
content type. Whenever the user hands you a research paper/article file — with
content of **any** type (not just DentAI), or with **no** متن at all — the paper
branch fires. Specified in **Phase C step 4.10** of
`.dentcast/workflows/README.md` (routed in **Phase 0**, armed by **Phase B
Question 4.7**):

1. **File the paper into Google Drive** — upload it into the correct *topical
   subfolder* (chosen semantically) of the cabinet folder
   `https://drive.google.com/drive/folders/1iDwq4Uj-y7_FO99-QW1Th0hVRN5yfk9f`.
2. **Enrich `dentcast_cabinet_full_catalog.json`** (repo root) — append the
   paper to its `papers` array with the Drive link, semantic hashtags (plus the
   article's own name), and the enriched-entry schema.
3. **First-author → DOI credit** — find the paper's DOI on the web, then credit
   the **first author** under the article with a link to the DOI, ShareHub-style.

**Routing by what was attached:**
- **Paper file + text (any type):** the page publishes normally for its type
  **and** all three actions run.
- **Paper file only, no text:** run **only actions 1 & 2** (Drive upload +
  catalog update) — **skip action 3** (no page to credit) and skip the rest of
  the publish flow. Drive upload + catalog edit + commit is the whole job.
- **Text, no paper file:** no paper actions; publish normally.

Hard guard for this trigger: **«اگر جایی شک داشتی سوال کن عمل نکن»** — anywhere
you're unsure (subfolder, topic/tags, DOI, first author), **ask first, never
guess.**

## Repo conventions

- **چالش** — a founder-authored **post whose body is a question**, published through the ordinary router into an existing folder (chairside/, insight/, whichever), taking that folder's next number and its ordinary brain shape — **never** a new `type`, **never** a new folder. Full design: `.dentcast/challenge-handoff.md`. Reading the question (+ image) is public, generated into `plus/challenges.json` by `tools/build_challenge_index.mjs`; **the answer and the 3–5 key points are never in the repo and never in any published file** — they live only in the `challenges` database table, written through `GET /admin` → «صندوق چالش». On submit, a model compares the reader's free-text answer against the key points and returns, per point, `covered`/`missing`/`unsure`; **any `unsure` queues the whole attempt** for the founder rather than guessing. `answer_fa` is released by ONE fact — the reader has an attempt row for this page — never by tier, so a lapsed reader who answered while premium keeps seeing it. Workflow hooks: Phase B **Question 4.9**, Phase C **step 4.14**. **The second documented exception to Hard Rule 12** (alongside LiteCast): no en mirror, no fa↔en toggle (RULE 16 — the mirror would be a different `content_id` with no row in `challenges`). **گفتگوی زیر مطلب never mounts under a چالش at all** (RULE 17, founder decision 2026-08-30) — a چالش already owns the reader's one interaction with the page, so the support-ticket-backed comment thread is not just reordered below it, it is absent; enforced inside `plus/js/article-threads.js`'s `mountArticleThreads()` itself (a `data-dc-challenge-question` scope check that returns `false`), never by an `if` at any of the four `plus.js` call sites — the same "data decides, call site never branches" shape RULE 9 already uses for mounting `mountChallenge` itself. **insight-68 is the reference implementation for the page markup** (RULE 18): the question and the image are `data-dc-challenge-question` / `data-dc-challenge-image` on the *same* `<p>`, never a separate visible `<img>` (a real `<img>` plus the JS-drawn copy is what rendered the photo twice on the first draft), and the image path is always site-absolute (`/insight/insight68.webp`, never a bare filename — a bare filename works by accident on the standalone page but 404s on the desktop 3-column shell, which injects the article's markup in place inside `index.html` rather than in an iframe). Both are enforced by `tools/build_challenge_index.mjs` (throws on a non-absolute path) and re-checked by `tools/verify_publish.py`'s چالش row (also confirms the `article-threads.js` guard above is still present).
- **تراز شواهد — the evidence-appraisal series, and the human half of DES** (`/taraz/`, brain `type` `taraz`, parts `taraz<chapter>-<part>`; founder, 1405/07/02). A section of its own on the پلاک صفر pattern — own root folder, own landing page (`taraz/index.html`, cloned from `plak-sefr/index.html`), own card — because a multi-part series on how to read a paper would be lost among twenty unrelated متانوت‌ها. It lives in the archive under **«سری‌های ویژه»**, the heading that used to read «بیرونِ درمان»: that group's real rule is FORMAT (bounded series that end: پرامپتولوژیست، پلاک صفر، تراز شواهد), not subject, so the heading now names the format and a new series never has to argue whether it is «inside treatment». Its pillar is `treatment-planning`, under the subtopic **`evidence-appraisal` («سنجشِ شواهد»)**, added with its first part — never `practice-infrastructure`, whose line is «a tool the reader operates», and appraisal is judgement, not a tool. Every part is a step of the **`evidence-literacy`** pathway, and part 1 is its FIRST step (`pathway_place.py --at-start`, which exists for exactly this: `--after` can only ever place something behind step one). **The planned link to DES is the reason for the name** (founder decision, recorded so a later session does not lose it): DES grades a source A–E, which is an assay («عیار/تراز»), and this series is meant to become the reader-facing explanation of what that grade measures, so the DES card and legend can later point into it. No such link exists yet; it is a founder decision to be made when the series is far enough along, not something to add in passing. Two consequences until then: its parts score on the **COMMENTARY** track like any authored page with no cited identifier, and `taraz/` is **not** in DES v2.4's closed item-4 carve-out table (chairside/metanotes/insight) — item 4 is earned from a sentence inside the part or not at all, and joining the table means a declaration on the landing page first and a spec bump after, never resemblance.
- `dentcast-brain.json` — central data file, has separate sections/arrays per content type.
- `dentcast-hashtag-reference.json` (repo root) — **the canonical hashtag library and single source of truth for every `#hashtag`** (the AI case-assistant search reads it, mirrored into `plus/content-index.json` by `tools/build_plus_index.mjs`). The reference owns the *vocabulary* (which canonical forms are legal, what each means, their aliases); the brain owns the *assignment* (which article carries which tag). **Standardized, never free text:** on every publish, resolve each proposed hashtag against this library and reuse the existing canonical form, or mint a new canonical concept (with `definition` + `use_when` + `aliases`) if genuinely absent — an alias is never used as a tag, a canonical tag is never filed as an alias, and no concept is duplicated. Tooling is `tools/hashtag_ref.py` (`--simulate`/`--apply`/`--sync`/`--check`); batches live in `.dentcast/hashtag-batches/`; governed by publishing-workflow **Hard Rule 15 / step 5.0** and seeded by `.dentcast/hashtag-campaign-handoff.md`.
- `dentcast_cabinet_full_catalog.json` — root catalog of the paper cabinet (`papers` array; mirrors the Google Drive folder's topical subfolders). Updated by the paper branch (workflow step 4.10); the search UI is `dentcast_cabinet_search.html`. **Its kebab-style `tags` are a SEPARATE system from the brain `#hashtags` above — not governed by the hashtag reference library.** Three things the cabinet now carries that a publish must not undo: it is **kept out of search** (`robots.txt` disallows the catalog and its `.enriched.json` sibling, `_headers` adds `X-Robots-Tag: noindex`, the page carries its own `<meta robots noindex>`) — never "fix" that and never sitemap it; on the site it is **premium** («کتابخانهٔ دنت‌کست», the second card of the archive tab's «موتور جستجوی دندانپزشکی» and the «کتابخانه» tool in the hamburger), gated on the tap by `plus/js/library-gate.js` (installed from `plus/js/header.js`, so it runs on every page), so verify a new paper by opening the search page directly; **the gate belongs to the DESTINATION, never to one element** — it is a delegated listener that catches every link whose path is the cabinet, plus the archive card, which is a `div[role=button]` and the only door carrying a lock badge. It was an inline script on `#card-library` alone until 2026-08-09, which is exactly why the desktop topbar icon and the hamburger's «کتابخانه» walked straight in; never re-bind it to a single id; and the card + its gate sheet advertise a **hand-written paper count** («بیش از ۲۲۰۰ مقاله») that step 4.10 sweeps on both surfaces when the total crosses a round hundred.
- `tools/` — Python scripts including the main index builder.
- **The topical index is one URL with two arrangements** (`/pillar/` and `/pillar/<slug>/`). `tools/build_pillar.py all` writes **two** files per structured pillar: the **page**, which lists every item of that pillar flat and newest-first (undated last) and is what every visitor and every crawler gets, and **`structure.json`** beside it, which carries the subtopic foldering and the reading-chain order. `/pillar/premium-index.js` fetches the sidecar and swaps it onto the *same* URL once `/me` confirms premium — no second page, no redirect, nothing to noindex. **Never hand-add subtopic cards back into a pillar page and never hand-edit a `structure.json`**: both arrangements in one document would put the same links on the page twice, which is the duplicate-content problem the split exists to avoid. Three consequences worth remembering: dates come from each target page's own JSON-LD `datePublished` (nowhere else has them) and are converted to the Persian calendar **at build time** because a crawler must read the date, not compute it; `tools/build_plus_index.mjs` reads its subtopic taxonomy from these sidecars, so it must run *after* the pillar builder; and `robots.txt` disallows the sidecars, which costs the premium layer nothing because robots rules never apply to a page's own fetch.
- **Cache-buster stamps.** Shared assets are loaded through a stamped URL (`/dc-nav.js?v=40`, `/plus/js/pricing-page.js?v=2`); the path never changes, so the stamp is the only thing that makes a returning browser fetch the new file. After changing **any** shared asset — including a module that a stamped entry merely *imports*, like `plus/js/premium-cta.js` — run `python3 tools/asset_version.py --bump` in the same commit. **Four of those assets are stamped by no page at all**: `plus/plus.js` and the three `plus*.css` files are appended at runtime by `dc-nav.js`, behind one hand-written constant (`var V`). The tool owns that constant too (`dc-nav.js:V` in the manifest, one fingerprint over all four graphs, raised before the HTML pass so `/dc-nav.js?v=` moves in the same run) — before it did, changing `plus.js` shipped a file every returning browser and the CDN kept serving from cache at the old stamp: deployed, live, and invisible, found only because somebody said a feature was missing (2026-08-12). It fingerprints each asset's whole import graph, raises the stale versions, rewrites every page, and updates `.dentcast/asset-versions.json`. CI runs `--check`. **And the modules those entries IMPORT are stamped too, by ONE shared number** (`modules:M` in the manifest; every internal `import`/`export from`/`import()` specifier in the module graph carries `?v=M`). Stamping only the entry was the same bug one level deeper: `/plus/plus.js?v=101` was a fresh URL on every bump, but its first line is `import … from './js/config.js'` and *that* URL never changed, so the browser refetched the entry and then satisfied all fifty-odd imports from cache — which is where nearly all of this codebase's behaviour lives. Found the same way as the `var V` case, by somebody saying a feature was missing (2026-08-15, the DES card's provenance line: the tinted card arrived because `plus.css` is stamped directly, the new text did not because `des.js` is not). **One number for every module, never one per entry** — a specifier is a URL, the same module is imported by several entries and by two spellings of its own path (`./api.js` and `/plus/js/api.js`), and two stamps on those two lines are two URLs, which the browser instantiates as two module objects with separate state; a per-entry stamp would have traded a caching bug for a much worse aliasing one. Three consequences: every hash goes through `hashable()`, which strips the stamps back out, or `--bump` would keep invalidating the fingerprint that justified it and never reach a fixed point; `dc-nav.js` is deliberately outside the module graph (a plain script with no imports — including it put the `var V` this same tool writes inside the module fingerprint, and the two passes took turns invalidating each other); and `spot/spot.js` is an explicit extra entry (`EXTRA_MODULE_ENTRIES`) because it is loaded by its own `SPOT_V` constant, so nothing would have found it — yet it imports `api.js`, which is exactly the double-instantiation above. **`SPOT_V` itself is owned by the tool now too** (`spot.js:SPOT_V`, one fingerprint over spot.js's graph, written to all three loaders): it is `var V`'s story a second time, except it had both failure modes at once, going stale when spot.js changed *and* drifting between its three hand-written copies — which is what happened (dc-nav.js on 30, both Plus views on 28 from 2026-08-12, so the dashboard and profile executed a four-version-old spot.js). Never hand-edit any of the three; the CI guard in `.github/workflows/spot-version-guard.yml` stays as an independent second check on a constant that has to be duplicated.

- **up-board — the reader-ordered view of the site** (`/up-board/`). **Three access levels, and the line between them is the design:** the page and «تازه‌ترین» are PUBLIC (every one of the 444 links, newest first); casting a قلب and reading a page's heart count need only a FREE signed-in account — charging for the act would starve the board of the signal it ranks by; and «بالاترین», the ranked arrangement (`GET /votes/board`, `requireAuth` + `requirePremium`), is PREMIUM. The gate is on the ARRANGEMENT, never the content — the identical split `pillar` already makes, so it is one rule applied twice rather than a new one. Its tab wears **amber** (never blue: amber means «this is what a subscription buys» site-wide) and is never removed or disabled — a reader who cannot open it must still see the second arrangement exists, or there is nothing to want. The gate distinguishes **three** answers, and conflating any two is a real bug: 401 = signed out (sign-in leads, the purchase link follows quieter — they may already be a subscriber logged out on this device), 402 = free (the premium card), anything else = «we could not ask», which must NEVER render as an upsell (a redeploy is minutes of exactly that; same reason `premium-cta.js`'s `unreachableGate` exists). The gate card says what the arrangement IS before what it costs — nobody buys an ordering they have never seen — and a `?sort=top` deep link falls back to the free list without popping the sheet unasked. `GET /votes/board` sets no `cache-control` of its own: `server.ts` stamps `no-store` on every response as a whole-API invariant, which a tier-dependent answer needs more than most. One page with TWO arrangements of the same 443 links: «تازه‌ترین» and «بالاترین». Deliberately one document, not two URLs — the same call `pillar` made, and for the same reason. Three parts, and the split between them is the design: **`up-board/index.json`** is the catalog (id/title/type/url/date), written only by `tools/build_upboard_index.py` on every publish (workflow step 5c) — never hand-edit it; **`GET /votes/board`** is the ordering, ids and numbers only, so a title can change without an API deploy; **`content_votes`** (migration 0040) is the one thing written down, because a heart is retractable and `user_activity` is append-only. Everything else is DERIVED, including the **engagement** behind every ranking — distinct users per action (comment/highlight/pin/share/finish), computed from `user_activity` **and `support_tickets`**, never stored. **گفت‌وگوی زیر مطلب tops the ladder at 4**, above a highlight, on the same rule that orders the rest of it by cost to the reader: a highlight is one second and nobody else sees it, a question is minutes of writing that goes to a person under the reader's own name. It was invisible to the score until 2026-08-12 — not underweighted, ABSENT, because commenting writes no `user_activity` row and earns no XP. Two properties come from the schema rather than a filter: **the founder's replies never count** (a ticket's `user_id` is the reader; an answer is a `ticket_messages` row that creates no ticket, so being responsive cannot raise your own pages) and **one reader is one voice** however long the thread runs. It counts WRITING, never publishing — `is_public` is the founder's editorial decision, and weighting by it would put that judgment inside a ranking whose whole claim is that it comes from readers. It reaches the score as a **percentile** (1–100, published as `engagement` and shown on each row with a tap-to-explain sheet), never a raw total: the raw numbers are skewed enough that any max-anchored scale squashes the middle of the site into single digits, and a percentile is the only 0–100 form of this that can be said out loud without lying — there is **no per-article view count anywhere on the site** (`view_stats` is per day+viewer, `spot_stats` per ad slot), so «٪ of readers» would be a percentage of nothing. **And that percentile is taken WITHIN a class** (`contentClass()`: `episodes/` = audio, everything else = readable), because an audio page cannot earn most of the seed — `highlight` and `pin` are three points each and neither door exists on a podcast, so on one shared scale its index measured how few ways it had to show interest rather than how much it drew. It is the same argument that made engagement a percentile at all, one level deeper: totals that are not comparable get compared as ranks. Deliberately **not** a weight — «a listen is worth ten» was the obvious other answer and is the same mistake the relative cap avoids: ten is calibrated to this year's mix, makes podcasts dominate the day they get busy, does nothing the day they go quiet, and lifts all 210 together instead of telling them apart. `MIN_CLASS_SIZE` (12) is the one guard — a percentile over three pages can only say 33/67/100 — and a class below it is ranked site-wide instead; `Board.engagement_scope` publishes which classes were ranked internally, because the sheet's sentence («more than ۶۲٪ of **podcasts**» vs «of the site») is a different claim in each regime and audio will not have twelve engaged pages on day one. That percentile buys at most `engagement_cap` points, and the cap is **relative**: `max(CAP_FLOOR, CAP_SHARE × mean hearts per voted page)`. A constant could only ever be right once — three points is most of the ranking while the busiest page has five hearts and noise once it has four hundred — so scaling it to the mean keeps its INFLUENCE steady rather than its value. `CAP_FLOOR` is what makes day one work: with no votes the relative term is zero, so the floor is what orders the board until votes arrive. **The cap is the guarantee, and the reason it is a cap and not a coefficient: a page with more hearts than the cap cannot be overtaken by engagement at all** — hearts stay the senior signal permanently, with no fade to schedule and no switch-over day. Sort is `score → hearts → engagement → id`, hearts ahead of engagement so the senior signal stays senior even inside a tie. Four rules the code depends on: **zero is never printed** — an empty heart invites, «۰ ❤» announces that nobody cared, and the threshold is 1 rather than a friendlier 5 so a printed count never differs between two people looking at the same page; **a vote earns nothing** — no XP, no streak, no `user_activity` row (the argument `score.ts` makes for excluding `content_shared` applies double to a one-second press, and score is never deducted); **there is no down-vote** and no column left for one — a down-arrow is a moderation tool for a site that publishes other people's submissions, and here it would only mark the founder's own clinical cases as bad in public; and **the page is `noindex, follow`, out of the sitemap, with its catalog disallowed in `robots.txt`** — every link on it is already indexed elsewhere and what it adds is an order a crawler cannot reproduce. Surfaces: the قلب button in the article's own action row (`plus/js/votes.js` mounts it into `#dcActionRow .dc-actions-main`; on the desktop shell, where dc-nav.js is stripped, `plus.js` builds that row itself — same gap `buildShareButton` closes), the page itself (`plus/js/upboard-page.js`), and the homepage `.dc-monitor` box's «بالاترین» tab + «همه ›» link (`plus/js/home-upboard.js`). Colour is `--heart`, a third semantic token — never amber (that means «this is what a subscription buys», and up-board is free) and never brand blue (a blue heart does not read as a heart). A published copy whose `Last-Modified` (which a cached edge response carries from the ORIGINAL object, so a stale copy declares its own age) predates `BUILT_AT` is now refused, and once a newer copy is adopted its own timestamp is the floor, so a later stale answer cannot roll it back (`ageFloor` in `content-refresh.ts`; both timestamps optional — a dev build or a header-less mirror keeps the old behaviour). Aliases are now bucketed by their **first token** — exact, not a heuristic, because `parts.every((p, k) => toks[i + k] === p)` can only succeed when `parts[0] === toks[i]` — with longest-first preserved inside each bucket, which is the only place two patterns can compete, and every `split` precomputed once per table. **And it was never "once per deploy"**: `content-refresh.ts` reloads the index every few minutes and both caches key on that reference, so each reload bought the next reader another stall. `test/case-assistant.test.ts`'s «the first round is not a stall» holds the order of magnitude (a one-second budget against 4.9s measured before), never a millisecond count that would flake on a busy box.
- **`plus/des-scores.json` — DentCast Evidence Score (DES), and its display contract.** The spec is `.dentcast/dentcast-evidence-score-v2.4.md`; the publish step that produces a record is workflow **4.13** (armed by Phase B **Question 4.8**). **Every spec version is ALSO published at the repo root** (`dentcast-evidence-score-v2.1.md`, `dentcast-evidence-score-v2.2.md`, `dentcast-evidence-score-v2.3.md`, `dentcast-evidence-score-v2.4.md`, …) and those copies are deliberate **public permalinks whose URLs have been shared outside this repository**. They cannot go stale either, because each filename carries its own version and is therefore a permalink to *that* version rather than a second copy of «current» — the same reason `.dentcast/` keeps v1.3 through v2.4 side by side. On every spec bump, add the new version at the root too and leave every older one in place. **The follow-up penalty (Step 4) does not exempt an SR/meta-analysis** (v2.3): unlike the sample-size penalty, which genuinely does not apply to a secondary study, the follow-up-duration penalty judges the survival/success *claim* being made, not the SR's own sample — so it fires against an SR exactly as it would a primary study whenever the SR's own text quotably supports a short-follow-up flaw. `dentai/dentai-30` is why: the identical input scored 55 in one run and 52 in another, because the 55-run copied the sample-size row's `"not applicable to a secondary study"` note onto the follow-up row instead of reading the paper's own limitations sentence about short follow-up in most included studies. 52 was correct. **The excluded-studies domain's `low` tier does not require a distinct reason per study** (v2.4): a reason genuinely shared by several individually-cited excluded studies is still "each with its reason," as long as it is specific and checkable rather than vague or citation-free. `dentai/dentai-30` moved from `some_concerns` to `low` on this domain for exactly that reason (four studies, named by citation, one specific shared reason) — its `des_score` was unaffected since the domain was never `high` either way. **A secondary report is not the study it reports** (v2.2): a consensus statement, guideline or conference synthesis carries its methods in the papers it summarises, so Question 4.8 follows the citation chain one level and scores **those** — the wrapper gets no record. Where the primaries are not retrievable, the wrapper is scored `text_basis: SECONDARY_REPORT`, which rates silence as `NR` and caps the multiplier at 0.75 exactly as `ABSTRACT_ONLY` does (an abstract condenses by length, a secondary report by role; in neither is a missing method evidence the study skipped it). `dentai/dentai-29` is why: its consensus statement was scored `FULL_TEXT` and rated `high` on search strategy, risk-of-bias appraisal and excluded studies — three claims that are false, since the two reviews it summarises searched three and five databases and both appraised independently. The tell was that the same document class scored 55/C from its abstract and 30/D from its full text, so **reading more of it made it worse**. **A transparency penalty is a SHARE of the design anchor, not a flat deduction** (v2.0 Step 4a): the table's numbers are `base_points` and what is subtracted is `max(1, round_half_up(base_points × S_design ÷ 100))`, so every penalty object carries both and Phase F recomputes the pair. **The AMSTAR-2 excluded-studies domain has THREE outcomes, not two** (v2.1 Step 3b-iii): a review that published no per-study list of excluded full-text studies is `some_concerns` when it reported **both** a screening account with counts (a PRISMA flow, or records screened → full texts assessed → included) **and** explicit inclusion/exclusion criteria; only a review documenting neither, or one of the two, is `high` — and that `high` still counts toward *critically low*. The old rule failed **9 of the 9** full-text reviews on record, and a domain nothing can pass ranks nothing; it also read a PROSPERO-registered five-database review with a PRISMA flow exactly like a narrative review with no Methods section. `ABSTRACT_ONLY` is untouched — silence there stays `NR`. A flat −8 was 8% of an SR's achievable range and 53% of a narrative review's, and below a certain anchor it exceeded the range entirely, so weak-design papers piled up on a floored 0 and stopped telling each other apart. The check is **version-gated** — records stamped `1.x` still validate against the flat table they were written under — and when it landed only 5 of 47 RESEARCH sources carried a penalty at all, with **no band moves**. Same machinery as `pathways.json`/`badges.json`: versioned in the repo, agent-written, no API deploy to change. The file is keyed by `content_id` (page path, no leading `/`, no `.html`) → `{scored_at, sources:[…]}`, and **`sources` holds the spec's output objects verbatim** — the spec owns that shape. **Nothing derivable is stored beside them** (no wrapper `band`, no `track`, no display strings): `content_type`, `band`, `question_type` and `provisional` already live inside each object, and a second copy is a second source of truth. It is **not** a brain field — Hard Rule 5 forbids adding one, and that is why this file exists at all. An absent `content_id` is how the display knows there is nothing to show, so a skipped publish writes **no key**, never a placeholder. **DES display rules** (mockups approved 2026-08-14): two placements and no others — a thin **chip** under the lead beside the date, and an **evaluation card** after the body and before the source citation; nothing mid-prose and nothing floating. The band is drawn as **five discrete blocks E→D→C→B→A with only the current one coloured**, never a gauge or a continuous bar, because the output is not continuous and a needle would give a two-point difference a meaning it does not have. **`question_type` is welded to the band and never shown apart from it** — bands are comparable only inside one question type, so an A on a bench test and an A on a clinical trial come from two different tables and must never read as equal. **A page citing SEVERAL papers gets a chip showing the RANGE** («۱۳ منبع · B–E»), coloured by the STRONGEST band in it. It showed the weakest until 2026-08-15, which reads as honest and is not: past a handful of citations the minimum is almost always E, so the chip carried no information and only ever read as bad news — `sharehub/share-14` cites two meta-analyses and an RCT and would have been labelled «از E» because it also cites a narrative review. The deeper error is about what a citation list is: sources are independent supports, not links in a chain, so adding a weak one cannot subtract the strong one already there, and a rule where adding evidence only ever lowers the score is backwards. The maximum alone is the opposite error (cherry-picking); the range says both and the card lists every source with its own band regardless. The 0–100 number rides **small and dim beside the band, never as a headline**: the band is what a reader judges with, the number is the audit layer. An `ABSTRACT_ONLY` score (`provisional: true`) wears a **hatched** block plus an «امتیاز مقدماتی» tag rather than a solid one. **A cited source with no method to appraise gets no score at all** — `content_type: "NOT_APPRAISABLE"` with `source_kind: "book"` (spec v1.9), rendered as a hollow chrome badge «کتاب مرجع» plus «امتیازدهی نمی‌شود», no band bar and no calculation block. A textbook is tertiary literature: no protocol, no search strategy, no risk-of-bias appraisal of what it summarises, so RoB 2 / AMSTAR-2 / QUIN / QUADAS-2 have nothing to measure and a number would have the shape of a measurement with none of the substance. It is not a low grade and not an error — it is the honest third answer, and it beats what happened without it: `sharehub/share-14` opens its «منابع» with *Global Diagnosis book* and was first scored on thirteen sources instead of fourteen, the book silently dropped. **DentCast's own authored content gets no band bar at all** — a «تجربهٔ بالینی» badge with its transparency score (e.g. ۱۷ از ۱۹) and the four transparency criteria, with band E kept behind a details toggle rather than deleted. Colour is its own third scale, **grey → dark green, never through red** — E is grey, not red, because a low band is not a failing grade and must not read as «رد شده»; it is never amber (that means «this is what a subscription buys») and never brand blue. **The card's own chrome is a FOURTH colour, indigo-violet (`--des-chrome`), and it carries no meaning at all** — its only job is to say a machine wrote this panel. Chroming it in the band scale is not the fix and is forbidden: every page DentCast authors is band E, so on exactly the pages where the problem is worst the band scale offers only grey, and a green-chromed card above a grey band would put the two systems in contradiction. Hence the card is **not** an article box (chrome-tinted fill, chrome border, one solid leading edge, a hairline seam in the gap above it), its heading names the machine («ارزیابی خودکار شواهد») with a provenance line ABOVE the content rather than a footnote below it, the «تجربهٔ بالینی» badge wears chrome rather than brand blue, and `interpretation_fa` is labelled «تفسیر امتیاز» and set apart from article typography — it is the longest block in the card and was the biggest single contributor to the misreading. Now the toolbar carries **↶ ↷ on its top row** (beside the hint line, no group label — the arrows act on the whole session while every other control acts on one piece of text, and sitting apart says so without a word; measured at 390px the bar gains ~10px and no row) and a **«🗑 حذف»** button in the selected-highlight group, which is also where «📝 یادداشت» and «🗂 کالکشن» live (the old «افزودنِ هایلایت به کالکشن» was a whole phone row; the buttons are disabled until a highlight is selected, and that state says «pick one first»). **Every entry in the stack is a pair of inverse SERVER calls**, never a DOM diff — each act is a request the moment it happens — and an entry moves from `done` to `undone` only AFTER its call resolves; a refused call leaves the pointer where it was (the stack must never drift from the server), `busy` serialises a double tap, any new act empties `undone` (history does not branch), and `exit()` clears it (per article, per session; never persisted — an id-shaped promise that fails on the first press is worse than an empty stack). **The inverse of «delete» is what forced the migration**: `DELETE /highlights/:id` was a hard delete, and `card_state` (the Leitner box) and `collection_items` (every board pin) cascade off it, so re-creating on undo minted a new id — a card back at box 1, pins gone, `?dcphl=` links dead — «something that LOOKS like the highlight». So delete is **soft** (`deleted_at`) and `POST /highlights/:id/restore` clears it; the same row comes back with card and pins untouched, and `highlight_restored` is logged rather than a second `highlight_created` (no XP for pressing ↶). **The base table is `highlights_all` and `highlights` is a VIEW over its live rows** — twenty-seven queries read that table (score, badges, monthly report, standings, concepts, consumption…) and a filter added at each is a filter the twenty-eighth forgets; the view makes every existing and future read correct by default, and only the two writes that must see deleted rows name `highlights_all` (the delete, the restore — and `merge-profiles.ts`, or a merge would leave the deleted rows to cascade away with the old account). The two counters that read `card_state` without the highlight (`GET /me` `due_card_count`, the review reminder sweep) join the view, and every board read carries `PIN_VISIBLE` so a hidden highlight's pin hides with it and returns with it. **No confirm dialog on حذف**, deliberately: the دفترچه confirms because it has no undo; here ↶ and the toast's own «بازگردانی» ARE the confirmation, and a better one, because they come after the act rather than in front of it. **The selected mark wears a ring** (`is-current`) — «current» had no visual at all before, so یادداشت/کالکشن acted on a mark the reader could not see was selected — and a click on plain prose clears it. **Colour and label edit the TAPPED highlight, never the one just created** (`_currentBy`): after a create they keep their old job of setting the default for the next mark, or «highlight A, then press green meaning the next one» would silently repaint A. `Ctrl/⌘+Z` and `Ctrl/⌘+Shift+Z` work outside a text field. Not decided: whether a soft-deleted row is ever purged — the stack lives one session and there is no trash surface, so after that the row is unreachable and costs a row; left as a founder decision. Tests: `plus-api/test/workbench-history.dom.test.ts` + the soft-delete block in `highlights.test.ts`.

Unlike a pathway (founder-curated) or a topic archive (auto-grouped by taxonomy), a collection is **entirely the user's own** — any mix of their own highlights and whole pages, no taxonomy coupling. Backend: `plus-api/src/routes/collections.ts` (full CRUD + idempotent item-add, all `requirePremium`). The catalog carries search + sort (تازه‌ترین/آخرین افزوده/پرمورد‌ترین/نام) and each board card shows `item_count` + `last_item_at`, which `GET /collections` **derives** (`max(ci.created_at)`) rather than storing — no column, no migration, no write path to keep true. A board page filters by kind (هایلایت/صفحه) and text. Both surfaces share `hl-view.js`; the chooser sheet (`chooserCard`) is one component used by both "add" and "move", and grows a filter box past six boards. Migration **0018** adds a board's own identity (`emoji`/`color`/`description`, all optional — a board with none renders exactly as before) and `collection_items.position`: **NULL means "never arranged"**, so an untouched board still opens newest-first, and `PUT /collections/:id/items/order` writes the **whole** order at once (empty array clears it), which is why there is no half-arranged state and a retry is a no-op. Arranging is a *mode* in the UI (`⇅ چیدمانِ دستی`): it collapses the masonry to one column, hides the filters (↑/↓ over a filtered subset would move an item past cards that aren't on screen) and gives each pin ↑/↓ + «۲ از ۷» — buttons, not drag, because dragging a masonry card is unusable on a phone and invisible to a keyboard. Migration **0036** (renumbered from the handoff's 0035 — `0035_ai_card_state` merged first and owns the number) adds two pin kinds a board originates itself («افزودن پین» chooser on the board header) plus board export — design ledger in `.dentcast/collections-pins-export-handoff.md`, whose decisions are made, not open: a **«متن خودم» text pin** and a **«رفرنس» reference pin** live in the `snippets` table (NOT "notes" — `article_notes` owns that word; one row, many pins via `collection_items.snippet_id`, a third partial unique index, and a one-kind XOR check), created-and-pinned atomically by `POST /collections/:id/snippets`, edited via `PATCH /snippets/:id` (kind immutable), re-pinned/moved through the same `POST .../items` with `{snippet_id}`. A reference's DOI metadata is fetched from Crossref **in the user's browser** (the container's international egress is unreliable; the API only stores what it's given) and manual entry is a first-class path, not a fallback — Persian journals mostly have no DOI. The **orphan rule**: removing a snippet's LAST pin deletes the snippet in the same transaction (there is no snippets library page, so an unpinned snippet would be invisible-but-alive forever); «انتقال» never trips it because it adds to the target before removing. No new XP kinds (pins fire the existing `collection_item_added`; «گنجینه» counts them automatically), and `GET /export/highlights` dumps `snippets` on ANY plan (data ownership). **Board export** («خروجی» on the board header): `GET /collections/:id/export?format=docx|pptx` builds the file server-side in memory (docx + pptxgenjs, pure JS, streamed, no temp files on the ephemeral disk) in the board's own display order — چیدمانِ دستی IS the slide/handout order. References collect into a numbered «منابع» section (Vancouver-ish, same `withDot` guard as the client's کپی‌استناد); RTL is per-paragraph (`bidirectional`/`rtl="1"` + right alignment on Persian, plain LTR on Latin citations). pptx passed the handoff §4.3 real-file gate on 2026-08-10; known accepted blemish: Google's Docs/Slides viewers ignore the rtl flag (bullets render left there) while real PowerPoint honors it. Deploying any of this needs an **API container rebuild** (new npm deps + migration 0036), not a content refresh.

- **تعطیلی مطب — clinic closures** (`plus-api/src/services/clinic.ts`, migration 0056). The contact card at `/card/` computes its own open/closed pill from the ordinary week (Sat-Wed, 12:30-19:00 Tehran — the same hours as `about.html`'s `openingHoursSpecification`; change them together), which is exactly why it spent a holiday telling visitors what time the clinic opens tomorrow. The closure dates therefore live in `clinic_closures`, written from the admin panel's «تعطیلی مطب» form (`GET`/`POST /admin/clinic`, `POST /admin/clinic/delete`) and read by the card through **`GET /clinic/status`** — the third sessionless route in this API, beside `/health` and `GET /threads/public`, because the caller is a card anonymous visitors open and the answer is about a door, not about a reader. **NO ROW MEANS NOTHING CHANGES**, and that is the whole safety argument: an empty table, an expired row, a dead API, no network at all — each leaves the card computing precisely the pill it computed before any of this existed. The API can only ever ADD a closure, never suppress one, so the feature cannot be the reason the card says nothing. Four rules the code depends on: the founder types **Jalali** dates (`services/jalali.ts` — converted by round-tripping ICU rather than a leap-year table of our own, so the two directions cannot disagree about which year is 366 days) while storage stays Gregorian like every other day in this API; a row is inclusive on both ends and an omitted end date means one day, which is the shape most closures have; **overlapping rows are legal and the latest end wins**, so extending a break is one more row rather than an edit, and `backOn()` names the first day somebody can actually walk in (skipping Thu/Fri and any further closure that starts there); and a founder-written `note` is printed **verbatim** — an empty note is not a missing field, it is the request for the sentence to be built from the dates in the card's own vocabulary («مطب تعطیل است · شنبه ۱۴ شهریور ساعت ۱۲:۳۰ باز می‌شود»). The pill waits up to 900ms for the answer rather than flashing «باز است» on a closed day, and a late answer still corrects the line. Tests: `plus-api/test/clinic.test.ts` + `clinic-card.dom.test.ts`.

- **مسیرها — pathway standings and the near-the-end alert** (`plus-api/src/services/pathway-standings.ts`, no migration). The founder-facing half of the pathway completion certificate, and it exists because nothing in the system could answer the one question the certificate plan depends on: **is anybody close?** Pathway progress is DERIVED (`pathways.ts` `computeProgress`) from the reader's own consumption, and `user_pathways` is a CACHE that `routes/pathways.ts` writes back only when the reader opens the pathway page — so a reader can go from step 2 to step 112 with no row changing anywhere. The progress exists; it had simply never been computed. `pathwayStandings()` computes it for everybody in **one** query (the same highlights ∪ `article_completed`/`episode_listened` union `consumption.ts` uses, narrowed to content that is a step of some pathway), and `runPathwayAlerts()` announces the crossings to the founder — nightly at `PATHWAY_ALERT_HOUR` (22:00 Tehran, `startPathwayAlertScheduler`), or on demand from the panel. Surfaces: the «مسیرها — چه کسی نزدیک پایان است» block on `GET /admin` over `GET /admin/pathways`, plus `POST /admin/pathways/run-alerts`. Five rules the code depends on. **The measure is `completed_steps`, never `current_step`** — the cursor stops at the first gap, so a reader who skipped step 2 and read the other 114 has `current_step = 1`; right for "resume here", off by a hundred for "how much is left". **The threshold is a COUNT of unread steps (`PATHWAY_NEAR_REMAINING`, 5), not a percentage**, because it answers "how long until an exam must be ready" and five articles is about the same amount of time whether the pathway has 17 steps or 116 — a percentage fires eleven early on the long ones and two late on the short ones. **Bundles are excluded**: 5–8 steps is not certificate-sized, and one for finishing six articles would spend the credibility of the one that means something. **Progress goes BACKWARDS and that is normal** — publishing step 5.6 files new content into existing pathways, so yesterday's finisher is today's «۲ قدم مانده» through no act of their own; hence the markers are a HIGH-WATER MARK (`user_activity` action `pathway_milestone`, `near` < `done`, written on the READER's row because it is a fact about them), the same shape `achievement-sync.ts` uses, and a pathway that grows under somebody never re-announces them. And **the alert is one message per RUN, not one per person** — the first sweep after this ships finds everybody who is already near the end, which is exactly the news that was missing, and fifty notifications is how that news gets muted instead of read; markers are claimed even when no alert phone is configured, so an unconfigured founder does not get week-old news re-announced every night (`PATHWAY_ALERT_PHONE`, falling back to `SUPPORT_ALERT_PHONE`). **The alert is for whoever SAID they want the certificate** (founder, 2026-09-12 — migration 0061): `alertable()` is `user_pathways.certificate_intent = 'wanted'` and nothing else — not enrolment (people enrol to track progress), not tier (premium gates sitting, not wishing), not closeness (that is what the alert measures). It used to be `enrolled || tier !== 'free'`, which is exactly how the founder came to write questions for readers who never wanted them. The question — «گواهی‌نامهٔ این مسیر را می‌خواهی؟», «بله» / «فعلاً نه» — is drawn by `intentRow()` in `pathways.js`, inside **`certificateStrip()`**, the one block under the pathway's progress bar (it replaced the separate exam card + question row on 2026-09-20), and on the dashboard's «مسیر یادگیری» block (`/me`'s `active_pathway.certificate_intent`) and the exam page. **The answer is a STATE, never a spent question.** It used to return null for any truthy `certificate_intent` — «فعلاً نه» included — and nothing else called `examIntent`, so a reader's answer was final in the UI although `setCertificateIntent` rewrites it happily, while the dashboard's own copy promised «هر وقت خواستی از صفحهٔ مسیر بگو» about a page that would never ask again. Now the row always shows the answer with «تغییر» / «نظرم عوض شد» beside it, and the pathway page acknowledges a «بله» the way the dashboard always did. **The tone follows progress, not a threshold**: with `completed_steps === 0` the strip INFORMS («این مسیر گواهی‌نامه دارد» + «می‌خواهمش») rather than asking — a wish declared at the start is cheap and one declared at step twelve is real — it asks plainly once anything has been read, and from `ready` on it stops asking entirely, because starting an attempt records the intent by itself. **And NO NUMBER appears anywhere in the strip, the catalog chip or the terms sheet** (founder, 1405/06/29): publishing step 5.6 files new content into existing pathways, so «۳۹ قدم» and «۴ قدم مانده» are true only until the next publish — the same argument the certificate sheet itself already makes. The exam page states its own form's rules, which are true by construction; `test/certificate-intent.dom.test.ts` asserts every other surface is digit-free. **The terms are a sheet of their own** (`plus/js/certificate-terms.js`, opened from the strip, the catalog's intro line, the exam page and the profile wall's locked card): what must be true (enrolment, every step, the exam, premium at the time of it) and what it buys, with the «امتیاز بازآموزی نیست» line moved in front of the decision instead of only under a certificate already issued. It exists because the terms lived only inside `contract()`, which renders only when a form's `rules` are in hand — so on every pathway with no form yet, the reader was asked to want something they could not read about. The catalog carries it too: `GET /pathways` returns `certifiable` / `certificate_intent` / `certificate_held` per pathway and `certChip()` draws one of four states, in the **certificate green** (`--dcp-cert`, never amber — that means «this is what a subscription buys» and these pages are already behind the subscription). `POST /exams/:id/intent` writes it (enrolling if needed — a wish about a pathway is being on it), starting the exam answers it by itself, and a «بله» from somebody already near the end runs `runPathwayAlerts(now, {only})` for that one pair at once — that answer IS the news and must not wait for 22:00; same markers, so the nightly run then has nothing new to say. **Every «بله» also reaches the founder on its own** (`notifyCertificateWish` in `pathway-standings.ts`, founder 1405/06/29), which the crossing sweep could not do: that one fires only within `PATHWAY_NEAR_REMAINING` of the end, so a wish at step three was recorded and announced to nobody — and a wish is exactly when there is still time to write the questions. It names whether that pathway already has a form (the actionable half; `hasForm` is passed IN because the form lives in `pathway-exams.ts`, which imports this module), is idempotent per (reader, pathway) on a `certificate_wish_alerted` marker — the action written as a LITERAL in the SQL, or `activity-vocabulary.test.ts` cannot see it — and goes `silent` when the crossing sweep has just named the same pair, because one event must not produce two notifications. **And a «بله» is now worth something to the READER too**: `notifyAssigneesOfNewForm` unions `user_pathways.certificate_intent = 'wanted'` with the hand-assigned, so writing a form tells everyone who asked for it — the card had been promising «در اطلاعیه خبرش را می‌گیری» with nothing on the other end of it. `declined` is kept, not deleted, so the admin table can say «گواهی نمی‌خواهد» instead of showing a gap; everyone else stays in the table with the answer on the row. **And that notification is not the only place a wish lands** (founder, 1405/06/30 — «اگر نوتیفو ندیدم با چک کردنش بفهمم»): `certificateWishes()` feeds the **«تقاضای گواهی‌نامه»** box on `GET /admin` (over `GET /admin/certificate-wishes`), the standing list of everybody who said «بله», with their pathway. It exists because the wish arrives exactly once, as a notification, and a notification is the one channel that can be missed — an unset `PATHWAY_ALERT_PHONE`, a muted push, a phone in another room — while the only other trace was a bold pill on a **standings** row, and that table answers a different question: it is sorted by distance from the END, with `walking` cut at forty, so a reader who asked at step three of thirty-nine was in practice invisible. Four things it does differently from the sweep beside it. It reads `user_pathways` DIRECTLY, never the standings, because a wish needs no progress at all — `certificateStrip()` offers «می‌خواهمش» at `completed_steps === 0` and `setCertificateIntent` enrols on the spot — so the wish is the row and progress is looked up beside it, zero when there is none. It carries **`has_form`** and the **live certificate** (`revoked_at is null`, the wall's rule), which is what lets it sort by what is OWED: no form first, closest to the end inside that, longest wait inside that, and a wish already answered with a certificate last — a record, not a job. It rolls the same rows up to the **pathway**, because one form serves everybody who wants that certificate and the founder's unit of work is never a person; the heading pill therefore counts only the wishes still owing a form. And it skips a non-certifiable pathway on the sweep's own rule — a bundle, a `certificate: 'pending'` pathway or an id that no longer resolves has no exam to prepare, so listing it would be a to-do nothing can close. Tests: `plus-api/test/pathway-alerts.test.ts` + the intent cases in `exams.test.ts` + `certificate-intent.dom.test.ts` + the certificate cases in `pathways.test.ts`.

- **گواهی تکمیل مسیر — pathway certificates, and the exam in front of them** (`plus-api/src/services/certificates.ts`, `services/pathway-exams.ts`, migration 0059). The `certificates` table has existed since migration 0001 (spec: "pathway-completion certificates (verification code, shareable)") and nothing ever wrote a row; 0059 keeps its shape and adds `holder_name`, `exam_id`, `revoked_at`, `discount_grant_id`. **What is WRITTEN is the decision** — one row, from `POST /admin/certificates/issue` on the «گواهی» panel block or from a passed exam attempt (see «آزمون مسیر» below) — the same move `badge_grants`/`pillar_grants` make; the standings sweep is an input to a person's decision, never a trigger. Four rules the code depends on. **The code is the point**: `services/reference.ts`, prefix `DC` (`DC-XXX-XXX`), the same no-0/O-1/I-5/S-8/B alphabet gift cards and tickets use, because it goes on a LinkedIn profile as the *credential ID* and is retyped by a stranger; minted with a savepoint-retry on the unique index rather than a longer code. **`holder_name` is frozen at issue, and it is the holder's REAL first name and family name** — never a join to `display_name` (a generated pseudonym that can be renamed), so the verify page can never disagree with the paper, and never a pseudonym in the first place (founder, 2026-09-20): the one thing that page asserts is that the person NAMED on the certificate finished the pathway, which a generated alias asserts about nobody. So every surface ASKS in two boxes — نام / نام خانوادگی, on the exam's start card and on the panel's hand-issue form — and **`services/holder-name.ts` is the single judge** of what may be printed: real whitespace only (a ZWNJ is not a space, Hard Rule 16 — «علی‌رضا» is one name), a leading title stripped before the parts are counted («دکتر مهسا» is one name, not two), no initials, no digit in either script, and nothing matching the generated-pseudonym shape (`isGeneratedPseudonym` in `pseudonym.ts`). Four doors carry it and `issueCertificate` is the LAST of them, so a row can never be written to a name a document cannot carry — which is what retired the old `holder_name || 'بدون نام'` fallback on the two issuing paths. Because a pass and its certificate commit together, a passing attempt whose stored name is not printable (only a row from before this rule) is **not settled at all**: it queues for the founder with that reason named in his ping, and `ruleAttempt` refuses a `pass` with `holder_name_invalid` until he types the real name into the field already in front of him. Tests: `plus-api/test/holder-name.test.ts` + the «the certificate carries a real name» block in `exams.test.ts`. **Revoked, never deleted** (`POST /admin/certificates/revoke`): the code may already be on somebody's profile, and a missing row reads as «never existed» where a revoked one says what happened. **The ٪۱۰ is written, never derived** — an ordinary `discount_grants` row (`kind: 'certificate'`, `CERTIFICATE_DISCOUNT_PERCENT`) in the same transaction, because pathway progress goes BACKWARDS whenever publish step 5.6 files new content into a pathway and a derived credit would vanish with it (`services/pathway-standings.ts` is the measurement; «رهرو» gold's `"all"` threshold is the live example); ten is one purchase's whole cap on purpose, spent whole. **A pathway may set its own** (`certificate_discount_percent` in `plus/pathways.json`, founder 1405/07/03 — «ارزیابی شواهد و استدلال بالینی», the pathway open to free accounts, mints ٪۲۰): a value ABOVE the cap is a **first-purchase** discount, kind `certificate_first` (`FIRST_PURCHASE_KIND` in `services/discount-credits.ts`), written as ONE row (never split) and decided at read time by `grantCredits` — no paid purchase yet on either rail → the whole percent, `outside_cap`, which `pickCredits` always takes and never counts toward the cap (a referred newcomer: ٪۲۰ + ٪۱۰); paid before → worth only the cap, inside it. That second branch is the point: «ستون» is only ever held by somebody who has paid, so a seat-holder stays at ٪۲۰ + ٪۱۰ and never reaches ٪۴۰–٪۵۰. «Paid before» excludes the payment that spent this very credit, so a spent one reads back at the percent it was spent at. ## Site-wide invariants

- **Google Analytics 4 (deferred) on every page.** Every HTML page MUST carry the deferred GA4 snippet (measurement ID `G-GMM0WC8X3M`) inside `<head>`. It is lazy-loaded — `gtag.js` is appended only after the `load` event so it never blocks first paint. Do NOT use Google's default async snippet; use the deferred pattern below. Because new pages are cloned from the most recent same-category page, the tag propagates automatically — but always confirm it survived the clone.
  - The canonical injector is `.github/scripts/inject_ga.py` (idempotent; skips pages that already have it, and pages without a `<head>`). To backfill/verify the whole site: `python3 .github/scripts/inject_ga.py` (or `--check` to fail if any page is missing it).
  - The build templates emit it too: `GA_DEFERRED_SNIPPET` in `tools/build_episodes.py` and `tools/build_pillar.py` (and the glossary head literal). Keep all of these in sync if the snippet ever changes.
  - The `.org` and `.ir` codebases are mirrors; the same tag intentionally deploys to both. Do NOT add per-domain logic.
  - The exact deferred snippet (place inside `<head>`):
    ```html
    <!-- Google Analytics (deferred: loads only after the page is fully rendered) -->
    <script>
      window.addEventListener('load', function () {
        window.dataLayer = window.dataLayer || [];
        function gtag(){ dataLayer.push(arguments); }
        window.gtag = gtag;
        gtag('js', new Date());
        gtag('config', 'G-GMM0WC8X3M');
        var ga = document.createElement('script');
        ga.async = true;
        ga.src = 'https://www.googletagmanager.com/gtag/js?id=G-GMM0WC8X3M';
        document.head.appendChild(ga);
      });
    </script>
    ```
  - If a Content-Security-Policy is ever added, it must allow `script-src https://www.googletagmanager.com` and `connect-src https://*.google-analytics.com https://*.analytics.google.com`. (No CSP currently exists in this repo.)

- **API preconnect on every page.** Every HTML page carries
  `<link rel="preconnect" href="https://api.dentcast.ir" crossorigin>` and the
  same for `.org`, at the very top of `<head>`. This is a paid-sponsor
  correctness issue, not a micro-optimisation: the Spot card cannot render
  until `/me` answers (that gate is what makes "premium sees no ads" true, and
  it is **not** to be relaxed), so on the first page of a tab the cold DNS +
  TLS handshake sat directly in front of the sponsor's impression — measured
  2.7–3.0s to first card, against 70–170ms on a refresh. Preconnect moves the
  handshake into HTML parsing instead.
  - Injector: `.github/scripts/inject_preconnect.py` (idempotent; `--check`
    fails if any page is missing it). `tools/build_pillar.py` emits
    `PRECONNECT_SNIPPET`; `tools/episodes_template.html` carries it inline.
  - **`crossorigin` is required and not decoration** — the API is called with
    credentials, and a connection opened in anonymous mode is not reused for a
    credentialed CORS request, so dropping it silently undoes the whole thing.
  - Both hosts are listed on every page on purpose: the two codebases are
    mirrors and per-domain logic is forbidden. The unused socket is idle and
    the browser drops it.

  `#dcActionRow` (`.dc-actions`) holds everything that used to sit between the
  title and the first paragraph. Until 2026-08-12 that area was **four
  independent bands from four injectors** — dc-nav.js's reading-time/share chip
  row, votes.js's قلب line, dc-nav.js's ToC, plus.js's میز کار bar — each doing
  its own `insertBefore(firstBox)`, so their **order was an accident of script
  load order** and their alignments (centre/centre/full-width/right) and button
  sizes agreed with nothing. Two groups, and the split IS the design:
  **`.dc-actions-main`** is what you can DO with the page (میز کار › افزودن به
  کالکشن › پسندیدم, in that order), **`.dc-actions-aux`** is what the page says
  about itself (زمان مطالعه) plus one courtesy (اشتراک‌گذاری). Five rules the
  code depends on. **No page carries this markup** — zero of the 197 article
  pages does, which is exactly why tidying the area cost no page edits and why a
  future change to it must stay in shared files. **Two builders, either order,
  both find-or-create**: `dc-nav.js` phase 7b builds the shell and fills the aux
  group (it is the only thing on the page that can count words before the module
  graph loads); `plus.js`'s `ensureActionRow` fills the main group, and builds
  the whole row itself on the desktop shell where dc-nav.js is stripped out of
  the fetched article. **The styles live in `plus.css`, never `dc-article.css`** —
  the shell keeps the former and strips the latter, and one row may not be
  defined in two stylesheets. **One button vocabulary** (`.dc-act` + a modifier:
  `-primary` filled, `-outline`, `-quiet`, `-heart`), same height and shape for
  all of them, so only weight and colour say which matters more — three
  different pill sizes in one row is precisely what read as clutter. And
  **زمان مطالعه is not a button**: as a `.dc-meta-chip` it was visually identical
  to the share pill beside it and a reader had to press it to learn it did
  nothing. The **ToC stays its own card**, below the row and above the prose — it
  is the one thing in that area that is content rather than a control. And the
  area has **three** anchors in `config.js`, not one: `findProseBox()` (the first
  box) for what goes ABOVE the article, `findProseRoot()` (the body as one
  element) for measuring, `findProseEnd()` (the last box) for what goes BELOW.
  On every page whose body is a single box all three agree, which is why picking
  the wrong one stays invisible — گفت‌وگوی زیر مطلب shipped anchored on
  `findProseBox()` and read correctly on 400-odd pages while opening after
  section 1 of 8 on the 26 legacy NoteCast pages. `findProseRoot()` is not the
  fix for that either: on exactly those pages it is `main.article-content-wrap`
  itself, so inserting after it lands outside the article shell. **Audio
  episodes get the SAME row an article does** — میز کار, افزودن به کالکشن, قلب,
  اشتراک‌گذاری, highlighting + یادداشتِ کلی on the caption/references, all
  through the same `setupWorkbench()` call — built by `initEpisodeActions()` on
  the standalone page and by `mountArticleWorkbench`'s episode branch on the
  desktop shell (2026-09-04; before that, episodes got a hand-built row with no
  میز کار at all — "highlighting a podcast makes no sense" — and that hand-built
  copy is also where a قلب-only-at-the-bottom bug lived: `initEpisodeActions()`
  ran synchronously and called `mountBottomActions()`, which always builds its
  own `.dcp-like`, before `boot()` ever reached `step('heart')`; `initHeart()`
  no-ops the instant any `.dcp-like` exists anywhere on the page, so the top row
  silently never got one). Episodes are excluded from the `article_completed`
  reading-streak signal inside `setupWorkbench()` (same guard as LiteCast) since
  they already have `episode_listened`. And the same two callers give an episode
  its **گفت‌وگوی زیر مطلب**,
  which had reached articles only because `initArticle()` mounts it and
  `initArticle()` bows out at the audio player. Nothing ever excluded a podcast:
  the block is written against a `content_id` and the API gates on nothing else,
  so it was unreachable rather than forbidden. Its anchor there is the single
  `.ep-box`, which puts the conversation under the whole episode card and above
  the ‹قبلی/بعدی› nav. Until 2026-08-12 they were the only content on the site a reader could
  not press پسندیدم on, while sitting in up-board's catalog like everything else
  (210 of its 444 entries) and earning engagement the score already counted
  (`episode_listened`). Nothing was added to `tools/episodes_template.html` for
  it: a row in the template would mean rebuilding 209 files for what the shared
  module puts there for free.

- **E-NAMAD trust seal (نماد اعتماد الکترونیکی) — three placements, dentcast.ir only.** The seal lives on exactly three surfaces and is **not** a per-page element: `index.html`'s `<footer>` (mobile shell), `index.html`'s `.dcd-a-seal` row in the col-A sidebar (desktop shell, where that footer is `display:none`), and `about.html`'s `.dc-trustseal-box` under the contact card. Do **not** clone it onto content pages — every copy is a request to enamad's server for zero trust value on an article page.
  - **This is the one deliberate exception to "no per-domain logic".** The seal is issued for a single domain (ours: `dentcast.ir`) and `trustseal.enamad.ir/logo.aspx` renders from the request's referrer, so on the `.org` mirror it answers with an *invalid seal* image. Two layers gate it: an inline `<head>` guard in both pages sets `dc-no-seal` on `<html>` off `.ir` (hides it before the body parses, no flash), and a block at the end of `dc-nav.js` removes the node outright. The images are `loading="lazy"` and both seals sit below the fold, so on `.org` the request normally never fires.
  - **The `<a>`/`<img>` attributes enamad verifies are copied verbatim and never rewritten** — `referrerpolicy='origin'`, `id`, `Code`, and the `code` attribute on the `<img>`. Only `alt`, `loading` and the wrapper are ours. The markup ships **statically in the HTML** (never JS-injected) so enamad's own crawler reads it.
  - Styling is `.dc-trustseal` in `dc-theme.css`, mirrored into `index.html`'s inline `<style>` (index loads no shared CSS). The chip is white in **both** themes on purpose — the seal artwork assumes a light background — and its box is fixed-size so nothing shifts when the image lands.
  - The desktop shell's reader strips `.dc-trustseal` along with the rest of the page chrome (`index.html`, chrome-removal selector list): `dc-nav.js` is stripped from that document, so a seal inside the iframe would escape the host gate.
