# DentCast Repo — Publishing Protocol

> **Agent parity — read before acting.** This repo is worked on by more than one
> agent (Claude Code, Cursor, Codex/GPT). The behavioral contract that makes
> their output identical — conversation language, which confirmation gates are
> never automatic, what to do when a capability (web search, Google Drive,
> ffprobe) is missing, the deterministic hash/build/validate commands, the
> output-parity checklist, and the git protocol — lives in
> **`.dentcast/workflows/agent-parity.md`**. `AGENTS.md` at the repo root is the
> agent-neutral mirror of this file, and `.cursor/rules/*.mdc` are Cursor's
> routers into the same canonical workflows.
>
> **Maintenance rule:** if you change a trigger, a rule, or a section here, make
> the same change to `AGENTS.md` and `.cursor/rules/dentcast-router.mdc` **in the
> same commit**. Logic lives in the canonical workflow files; routers only point
> at them; behavior lives in `agent-parity.md`. None of them duplicates another.

This repo powers DentCast. When the user brings new content to publish:

1. Read `.dentcast/workflows/README.md` and follow it strictly.
2. `dentcast-brain.json` is the source of truth for every content type's structure, schema, and category. Always use the most recent entry of the SAME category as the template for any new entry.
3. Never mix categories. NoteCast stays in NoteCast. Insight stays in Insight. Each category's entries go to their own section/array in the brain and their own directory on disk.
4. The "latest content" widget on the homepage reads the LAST entries from `dentcast-brain.json`. Therefore, every new entry MUST be appended at the END of its category in the brain — never inserted mid-list.
5. Auto-discover whatever you can. Ask the user only for things you genuinely cannot determine.
6. Brain entry schema is sacred. Never add new fields to a brain entry that don't exist on previous same-category entries. Match the existing shape exactly.
7. A string the user supplied is **copied, not re-typed** (Hard Rule 16). A ZWNJ (`U+200C`) is not a space — «اندو‌شده» ≠ «اندو شده» — and widening their caption by a clause is a rewrite, not a copy. Propose changes; never make them in passing.
8. Correcting a title or caption after the fact is a **sweep, not a spot edit** (Hard Rule 17). A title lives on ~8 surfaces and a caption on ~4 (including the en mirror); all of them change in the same commit, then the builders re-run.
9. **A publish ends with a green gate, not with a claim.** After Phase E, run Phase F and paste its summary line into the report:
   ```bash
   python3 tools/verify_publish.py <content_id> \
     --expect-title "<title exactly as the user wrote it>" \
     --expect-caption "<caption exactly as the user wrote it>"
   ```
   Non-zero exit = the publish is incomplete. Every `FAIL` row prints its own fix command. The gate does not replace any step — it catches what a long checklist forgets (a builder run out of order, a surface a correction missed, an invisible character that changed).
10. **Every publish is scored — DES runs the prompt file, and a DOI is never guessed.** Phase B **Question 4.8** sorts the publish into one of three baskets and Phase C **step 4.13** does the work: load `.dentcast/dentcast-evidence-score-v1.5.md` as the system prompt (whole file, minus its appendix — that appendix is the pipeline contract you run yourself), one input block **per cited source**, then store the output verbatim in `plus/des-scores.json`. **The scoring model never fetches**, so `source_text` must be resolved *before* the prompt runs — local cabinet first, then PubMed MCP, then WebFetch — and a source whose abstract you could not retrieve ends as `INSUFFICIENT_TEXT`, never as a score assembled from the DentCast متن about it. The third basket is the one that always stops: research-shaped content with **no identified paper** (an episode with only a caption and audio) is asked as two named options — «DOI می‌دم» or «بدون DES منتشر بشه» — and there is no third answer, in particular not scoring it as COMMENTARY to have something. Skips are LiteCast and the user's own «بدون DES»; both are reported, never silent.

## English-version protocol (trigger)

There is a **second** workflow alongside the publishing router. When the user
asks to produce the **English (en) version of an existing page** — trigger
phrase **«… رو انگلیسی کن»** (e.g. «پرامپتولوژیست ۱ رو انگلیسی کن»,
«نسخه‌ی انگلیسیِ متانوت ۳») — do **not** use the «متن جدید دارم» publishing
router. Instead read `.dentcast/workflows/en-version.md` and follow it
strictly. That workflow mirrors one existing page into
`/{type}/en/{same-filename}.html`: English chrome cloned from
`metanotes/en/meta-1.html`, body/schema inherited and translated from the
source's own type, and a real per-document fa↔en toggle on both sides. en
pages are standalone translations AND a reader-only surface: they ship
**noindexed** (`noindex, follow`, zero hreflang, out of the sitemap — they
are unreviewed AI translations; 2026-08-11 SEO audit) and get **no**
`dentcast-brain.json` entry, **no** Pulse line, and **no** specialist
cross-linking.

**Note — the publishing router already invokes this workflow automatically.**
Every normal `.org` publish ends with **Phase D** of
`.dentcast/workflows/README.md`, which runs this same en-version workflow on
the page it just published — so a freshly published page **always** ships with
its English mirror + a working fa↔en language toggle (Hard Rule 12), never a
toggle-less page. The **«… رو انگلیسی کن»** trigger therefore remains for
mirroring an **older/pre-existing** page that predates that rule (or any page
whose en version is missing) — it is the on-demand entry point to the *same*
machinery the router now calls on its own. **LiteCast is the sole exception:**
it is `.ir`-only with no hreflang, so it gets no en mirror or toggle in either
path.

## Ad-publishing protocol (trigger)

There is a **third** workflow alongside the publishing router and the
en-version router. When the user says they have an **advertisement** to
publish or manage — trigger phrases like **«تبلیغ دارم»**, «آگهی دارم»,
«اسپانسر گرفتیم», «تبلیغ X رو خاموش کن», «سهم اسپانسر رو کم/زیاد کن» — do
**not** use the «متن جدید دارم» publishing router. Instead read
`.dentcast/workflows/ads.md` and follow it strictly. An ad is not content:
it gets **no** page, **no** brain entry, **no** Pulse line, **no** en mirror
— the whole ad system lives in `spot/spot-config.json` (see `spot/README.md`).
That workflow interviews for the gaps (sponsor vs internal, link, copy,
image, slots, rotation share) and files sponsors so they automatically ship
with `rel="sponsored"` (Google compliance). Never hardcode an ad into a page.
**Always ask which of the four زمان‌ها (rotation beats) the new ad takes and
what fills the rest** — the rotation advances once per **ad-showing page
view**, so a four-entry `rotation.sequence` = four page views (four refreshes,
or four articles, is one full lap), and an ad assigned to no beat renders never
(ads.md hard rule 6 + Phase B question 6).

## Ad-reporting protocol (trigger)

When the user asks for **ad numbers** — «گزارش تبلیغ بده», «آمار تبلیغات»,
«تبلیغ‌ها ماه گذشته چقدر دیده شدن؟», «کلیک اسپانسر X چقدر بوده؟» — read
`.dentcast/workflows/spot-report.md` and follow it. This is read-only: no
config edit, no publish. Every ad render/click already reports to **our own
API** (`spot_impression`/`spot_click` → aggregate counters, read back via
`GET /admin/spot/stats` — or, already formatted, the **«گزارش تبلیغ‌ها»** section
of the `GET /admin` page, with its three windows ۲۴ ساعت/۷ روز/۳۰ روز and each
تبلیغ broken down by محل) **and** to GA4 as a cross-check, so the report is a
lookup, not a build. **«۲۴ ساعت» there is the Tehran calendar day, never a
rolling window** — `spot_stats` is keyed by day and carries no hour, so a real
last-24-hours figure does not exist in this data and must not be implied. Our API is the source of truth: adblockers drop GA but
not a same-site subdomain. Three rules that decide whether the answer is
right: the headline number is always **تعداد بارِ نمایش** (one person seeing
an ad 20 times is 20 — there is deliberately no per-user attribution, so
"چند نفر" is unanswerable), **premium is zero by design, not by
measurement**, and no data of any kind exists before 2026-07-26. Numbers are
never guessed — if the data isn't in hand, hand over the command instead.

## Attached paper file (trigger — ANY type, file-driven)

The paper actions are triggered by the **paper file itself**, *not* by the
content type. Whenever the user hands you a research paper/article file — with
content of **any** type (not just DentAI), or with **no** متن at all — the paper
branch fires. Specified in **Phase C step 4.10** of
`.dentcast/workflows/README.md` (routed in **Phase 0**, armed by **Phase B
Question 4.7**):

1. **File the paper into Google Drive** — upload it into the correct *topical
   subfolder* (chosen semantically) of the cabinet folder
   `https://drive.google.com/drive/folders/1iDwq4Uj-y7_FO99-QW1Th0hVRN5yfk9f`.
2. **Enrich `dentcast_cabinet_full_catalog.json`** (repo root) — append the
   paper to its `papers` array with the Drive link, semantic hashtags (plus the
   article's own name), and the enriched-entry schema.
3. **First-author → DOI credit** — find the paper's DOI on the web, then credit
   the **first author** under the article with a link to the DOI, ShareHub-style.

**Routing by what was attached:**
- **Paper file + text (any type):** the page publishes normally for its type
  **and** all three actions run.
- **Paper file only, no text:** run **only actions 1 & 2** (Drive upload +
  catalog update) — **skip action 3** (no page to credit) and skip the rest of
  the publish flow. Drive upload + catalog edit + commit is the whole job.
- **Text, no paper file:** no paper actions; publish normally.

Hard guard for this trigger: **«اگر جایی شک داشتی سوال کن عمل نکن»** — anywhere
you're unsure (subfolder, topic/tags, DOI, first author), **ask first, never
guess.**

## Repo conventions

- `dentcast-brain.json` — central data file, has separate sections/arrays per content type.
- `dentcast-hashtag-reference.json` (repo root) — **the canonical hashtag library and single source of truth for every `#hashtag`** (the AI case-assistant search reads it, mirrored into `plus/content-index.json` by `tools/build_plus_index.mjs`). The reference owns the *vocabulary* (which canonical forms are legal, what each means, their aliases); the brain owns the *assignment* (which article carries which tag). **Standardized, never free text:** on every publish, resolve each proposed hashtag against this library and reuse the existing canonical form, or mint a new canonical concept (with `definition` + `use_when` + `aliases`) if genuinely absent — an alias is never used as a tag, a canonical tag is never filed as an alias, and no concept is duplicated. Tooling is `tools/hashtag_ref.py` (`--simulate`/`--apply`/`--sync`/`--check`); batches live in `.dentcast/hashtag-batches/`; governed by publishing-workflow **Hard Rule 15 / step 5.0** and seeded by `.dentcast/hashtag-campaign-handoff.md`.
- `dentcast_cabinet_full_catalog.json` — root catalog of the paper cabinet (`papers` array; mirrors the Google Drive folder's topical subfolders). Updated by the paper branch (workflow step 4.10); the search UI is `dentcast_cabinet_search.html`. **Its kebab-style `tags` are a SEPARATE system from the brain `#hashtags` above — not governed by the hashtag reference library.** Three things the cabinet now carries that a publish must not undo: it is **kept out of search** (`robots.txt` disallows the catalog and its `.enriched.json` sibling, `_headers` adds `X-Robots-Tag: noindex`, the page carries its own `<meta robots noindex>`) — never "fix" that and never sitemap it; on the site it is **premium** («کتابخانهٔ دنت‌کست», the second card of the archive tab's «موتور جستجوی دندانپزشکی» and the «کتابخانه» tool in the hamburger), gated on the tap by `plus/js/library-gate.js` (installed from `plus/js/header.js`, so it runs on every page), so verify a new paper by opening the search page directly; **the gate belongs to the DESTINATION, never to one element** — it is a delegated listener that catches every link whose path is the cabinet, plus the archive card, which is a `div[role=button]` and the only door carrying a lock badge. It was an inline script on `#card-library` alone until 2026-08-09, which is exactly why the desktop topbar icon and the hamburger's «کتابخانه» walked straight in; never re-bind it to a single id; and the card + its gate sheet advertise a **hand-written paper count** («بیش از ۲۲۰۰ مقاله») that step 4.10 sweeps on both surfaces when the total crosses a round hundred.
- `tools/` — Python scripts including the main index builder.
- **The topical index is one URL with two arrangements** (`/pillar/` and `/pillar/<slug>/`). `tools/build_pillar.py all` writes **two** files per structured pillar: the **page**, which lists every item of that pillar flat and newest-first (undated last) and is what every visitor and every crawler gets, and **`structure.json`** beside it, which carries the subtopic foldering and the reading-chain order. `/pillar/premium-index.js` fetches the sidecar and swaps it onto the *same* URL once `/me` confirms premium — no second page, no redirect, nothing to noindex. **Never hand-add subtopic cards back into a pillar page and never hand-edit a `structure.json`**: both arrangements in one document would put the same links on the page twice, which is the duplicate-content problem the split exists to avoid. Three consequences worth remembering: dates come from each target page's own JSON-LD `datePublished` (nowhere else has them) and are converted to the Persian calendar **at build time** because a crawler must read the date, not compute it; `tools/build_plus_index.mjs` reads its subtopic taxonomy from these sidecars, so it must run *after* the pillar builder; and `robots.txt` disallows the sidecars, which costs the premium layer nothing because robots rules never apply to a page's own fetch.
- **Cache-buster stamps.** Shared assets are loaded through a stamped URL (`/dc-nav.js?v=40`, `/plus/js/pricing-page.js?v=2`); the path never changes, so the stamp is the only thing that makes a returning browser fetch the new file. After changing **any** shared asset — including a module that a stamped entry merely *imports*, like `plus/js/premium-cta.js` — run `python3 tools/asset_version.py --bump` in the same commit. **Four of those assets are stamped by no page at all**: `plus/plus.js` and the three `plus*.css` files are appended at runtime by `dc-nav.js`, behind one hand-written constant (`var V`). The tool owns that constant too (`dc-nav.js:V` in the manifest, one fingerprint over all four graphs, raised before the HTML pass so `/dc-nav.js?v=` moves in the same run) — before it did, changing `plus.js` shipped a file every returning browser and the CDN kept serving from cache at the old stamp: deployed, live, and invisible, found only because somebody said a feature was missing (2026-08-12). It fingerprints each asset's whole import graph, raises the stale versions, rewrites every page, and updates `.dentcast/asset-versions.json`. CI runs `--check`.
- `index.html` — homepage with Pulse section + latest-content widget.
- Each content type has its own directory at the repo root (e.g., `/notecast/`, `/insight/`, `/litecast/`, etc.). Confirm exact paths from the URLs stored in brain entries.
- `.dentcast/workflows/` — publishing workflows (+ `agent-parity.md`, the cross-agent behavior contract).
- `AGENTS.md` (repo root) — agent-neutral mirror of this file, for Cursor / Codex / any other agent. `.cursor/rules/*.mdc` — Cursor routers into the same canonical workflows. All three are kept in sync (see the maintenance rule at the top).
- **up-board — the reader-ordered view of the site** (`/up-board/`). **Three access levels, and the line between them is the design:** the page and «تازه‌ترین» are PUBLIC (every one of the 444 links, newest first); casting a قلب and reading a page's heart count need only a FREE signed-in account — charging for the act would starve the board of the signal it ranks by; and «بالاترین», the ranked arrangement (`GET /votes/board`, `requireAuth` + `requirePremium`), is PREMIUM. The gate is on the ARRANGEMENT, never the content — the identical split `pillar` already makes, so it is one rule applied twice rather than a new one. Its tab wears **amber** (never blue: amber means «this is what a subscription buys» site-wide) and is never removed or disabled — a reader who cannot open it must still see the second arrangement exists, or there is nothing to want. The gate distinguishes **three** answers, and conflating any two is a real bug: 401 = signed out (sign-in leads, the purchase link follows quieter — they may already be a subscriber logged out on this device), 402 = free (the premium card), anything else = «we could not ask», which must NEVER render as an upsell (a redeploy is minutes of exactly that; same reason `premium-cta.js`'s `unreachableGate` exists). The gate card says what the arrangement IS before what it costs — nobody buys an ordering they have never seen — and a `?sort=top` deep link falls back to the free list without popping the sheet unasked. `GET /votes/board` sets no `cache-control` of its own: `server.ts` stamps `no-store` on every response as a whole-API invariant, which a tier-dependent answer needs more than most. One page with TWO arrangements of the same 443 links: «تازه‌ترین» and «بالاترین». Deliberately one document, not two URLs — the same call `pillar` made, and for the same reason. Three parts, and the split between them is the design: **`up-board/index.json`** is the catalog (id/title/type/url/date), written only by `tools/build_upboard_index.py` on every publish (workflow step 5c) — never hand-edit it; **`GET /votes/board`** is the ordering, ids and numbers only, so a title can change without an API deploy; **`content_votes`** (migration 0040) is the one thing written down, because a heart is retractable and `user_activity` is append-only. Everything else is DERIVED, including the **engagement** behind every ranking — distinct users per action (comment/highlight/pin/share/finish), computed from `user_activity` **and `support_tickets`**, never stored. **گفت‌وگوی زیر مطلب tops the ladder at 4**, above a highlight, on the same rule that orders the rest of it by cost to the reader: a highlight is one second and nobody else sees it, a question is minutes of writing that goes to a person under the reader's own name. It was invisible to the score until 2026-08-12 — not underweighted, ABSENT, because commenting writes no `user_activity` row and earns no XP. Two properties come from the schema rather than a filter: **the founder's replies never count** (a ticket's `user_id` is the reader; an answer is a `ticket_messages` row that creates no ticket, so being responsive cannot raise your own pages) and **one reader is one voice** however long the thread runs. It counts WRITING, never publishing — `is_public` is the founder's editorial decision, and weighting by it would put that judgment inside a ranking whose whole claim is that it comes from readers. It reaches the score as a **percentile** (1–100, published as `engagement` and shown on each row with a tap-to-explain sheet), never a raw total: the raw numbers are skewed enough that any max-anchored scale squashes the middle of the site into single digits, and a percentile is the only 0–100 form of this that can be said out loud without lying — there is **no per-article view count anywhere on the site** (`view_stats` is per day+viewer, `spot_stats` per ad slot), so «٪ of readers» would be a percentage of nothing. **And that percentile is taken WITHIN a class** (`contentClass()`: `episodes/` = audio, everything else = readable), because an audio page cannot earn most of the seed — `highlight` and `pin` are three points each and neither door exists on a podcast, so on one shared scale its index measured how few ways it had to show interest rather than how much it drew. It is the same argument that made engagement a percentile at all, one level deeper: totals that are not comparable get compared as ranks. Deliberately **not** a weight — «a listen is worth ten» was the obvious other answer and is the same mistake the relative cap avoids: ten is calibrated to this year's mix, makes podcasts dominate the day they get busy, does nothing the day they go quiet, and lifts all 210 together instead of telling them apart. `MIN_CLASS_SIZE` (12) is the one guard — a percentile over three pages can only say 33/67/100 — and a class below it is ranked site-wide instead; `Board.engagement_scope` publishes which classes were ranked internally, because the sheet's sentence («more than ۶۲٪ of **podcasts**» vs «of the site») is a different claim in each regime and audio will not have twelve engaged pages on day one. That percentile buys at most `engagement_cap` points, and the cap is **relative**: `max(CAP_FLOOR, CAP_SHARE × mean hearts per voted page)`. A constant could only ever be right once — three points is most of the ranking while the busiest page has five hearts and noise once it has four hundred — so scaling it to the mean keeps its INFLUENCE steady rather than its value. `CAP_FLOOR` is what makes day one work: with no votes the relative term is zero, so the floor is what orders the board until votes arrive. **The cap is the guarantee, and the reason it is a cap and not a coefficient: a page with more hearts than the cap cannot be overtaken by engagement at all** — hearts stay the senior signal permanently, with no fade to schedule and no switch-over day. Sort is `score → hearts → engagement → id`, hearts ahead of engagement so the senior signal stays senior even inside a tie. Four rules the code depends on: **zero is never printed** — an empty heart invites, «۰ ❤» announces that nobody cared, and the threshold is 1 rather than a friendlier 5 so a printed count never differs between two people looking at the same page; **a vote earns nothing** — no XP, no streak, no `user_activity` row (the argument `score.ts` makes for excluding `content_shared` applies double to a one-second press, and score is never deducted); **there is no down-vote** and no column left for one — a down-arrow is a moderation tool for a site that publishes other people's submissions, and here it would only mark the founder's own clinical cases as bad in public; and **the page is `noindex, follow`, out of the sitemap, with its catalog disallowed in `robots.txt`** — every link on it is already indexed elsewhere and what it adds is an order a crawler cannot reproduce. Surfaces: the قلب button in the article's own action row (`plus/js/votes.js` mounts it into `#dcActionRow .dc-actions-main`; on the desktop shell, where dc-nav.js is stripped, `plus.js` builds that row itself — same gap `buildShareButton` closes), the page itself (`plus/js/upboard-page.js`), and the homepage `.dc-monitor` box's «بالاترین» tab + «همه ›» link (`plus/js/home-upboard.js`). The homepage's **«دسته‌های محتوا» grid is not to be moved or removed**: `spot.js`'s `renderHome` anchors the mobile ad to `.dc-exa-cats`, so touching it relocates paid sponsor inventory. Colour is `--heart`, a third semantic token — never amber (that means «this is what a subscription buys», and up-board is free) and never brand blue (a blue heart does not read as a heart). Tests: `plus-api/test/votes.test.ts` + `votes.dom.test.ts` + `upboard-page.dom.test.ts` + `home-upboard.dom.test.ts`.
- `spot/` — central config-driven ad system ("Spot"; the name is deliberately neutral — EasyList's generic `##.dc-ad` rule hid the old `/ads/` + `dc-ad` naming under every adblocker, so never use "ad/ads" in this system's file names, paths, classes, ids, or data attributes). `spot/spot-config.json` is the single source of truth (master + per-slot on/off, premium/sponsor creatives, rotation sequence, per-creative `slots`/`audience` targeting); `spot/spot.js` is injected on every page by a loader hook at the end of `dc-nav.js`. Anonymous + free Plus users see ads; premium users see none; anything switched off leaves zero trace. Docs: `spot/README.md`. No page carries ad markup — never hardcode ads into pages.
- `plus/pathways.json` — DentCast Plus learning pathways (spec §5 schema; premium Phase 3). A pathway is a curated learning journey, **not** a pillar view: unlike a pillar (one home per item), the **same item can belong to many pathways**, placed at the right prerequisite→advanced position in each. Every specialist publish assigns the new content to its pathway(s) via **workflow step 5.6** (semantic, ask-if-unsure). Tools: `tools/pathway_place.py` (placement proposal + `--insert` + `--coverage`) and `tools/pathway_scout.py` (candidate search + `--steps` + `--coverage`). Catalog/doctrine: `reports/pathways-catalog-2026-07-22.md`. Backend infra is live — `plus-api/src/pathways.ts` loads it (cached, reload-on-change like `content-index.ts`) and `GET/POST /pathways*` (premium-gated) + `GET /me`'s `active_pathway` read through it; `user_pathways` holds enrollment + a derived `current_step`/`completed_at` cache (never advanced by a client call — recomputed from highlights/`user_activity` on every read). Editing the file no longer needs an API redeploy: the baked `PATHWAYS_PATH` copy is only the boot value, and `plus-api/src/content-refresh.ts` re-fetches the published `plus/pathways.json` (and `plus/content-index.json`) from the live site every few minutes — validated, upgrade-only, last-good-copy on any failure. Frontend is live too — `/plus/pathways.html` (catalog), `/plus/pathway.html?id=` (step list + enroll), and a "مسیر یادگیری" block on the `/plus/` dashboard (`plus/js/pathways.js` is the shared renderer). **Starter bundles** (`kind: "bundle"` entries, appended after the 15 full pathways) are a short, curated subset of one pathway's steps — "just the core" in 5–8 steps, never a new pathway of their own. Schema adds `kind`/`glyph`/`prereq_bundle`/`continues_pathway` on the pathway object only (steps stay `{content_id, milestone}`); catalog, doctrine, and the "which item belongs in a bundle" editorial rule live in `.dentcast/bundles-handoff.md`. **Workflow step 5.6 places new content into full pathways; step 5.6-ب then runs the bundle gate chain** — five mechanical yes/no gates (folder type ∈ episodes/notecast/sharehub/dentai; title names a whole concept, not a case/trick/نکته; fills a coverage hole no current step covers; no twin already inside; ≤ 8 steps after). All five pass → auto-insert mid-list at a semantic anchor (never at the end — the last step owns the 🏁 milestone); any doubt, any replacement, or an end-of-list position → ask the founder. Every candidate bundle gets an explicit verdict in the publish report, and any bundle edit sweeps `plus/js/home-bundles.js`'s step count + `asset_version.py --bump` in the same commit. Surfaced on the homepage as the "از کجا شروع کنم؟" rail (`plus/js/home-bundles.js`) ahead of the catalog's "باندل‌های شروع" section.
- `plus/badges.json` — the achievement catalog behind the profile's «افتخارات» section (two league medals + 25 badges). Same machinery as `pathways.json`: versioned in the repo, loaded by `plus-api/src/badges.ts` (reload-on-change, remote copy wins, last-good on error), re-fetched live by `content-refresh.ts`, so **retuning a threshold or rewriting a badge's Persian copy is a commit to the site, not an API deploy**. Served by `GET /achievements` (`plus-api/src/routes/achievements.ts`), rendered by `plus/js/achievements.js` into `profile.js` between «رکوردها» and «لیگ من». Four rules the code depends on: **every badge is DERIVED, never written down** (`plus-api/src/services/achievements.ts` computes every metric from data that already exists) — which is what makes the whole shelf retroactive, with no `earned_at` column that could disagree with the log it came from and no backfill on launch day; **one comparison, `value >= threshold`**, so anything naturally inverted (signup order in «پیشگام») is normalised to a 0/1 in the service rather than teaching the evaluator a second direction; **a level is a ring colour, never a word** — the wall never writes «طلا», only the medal row does and there it never stands alone («طلای کامپوزیت»), because two metal scales share the section (the league's seven dental materials and the badges' bronze/silver/gold) and the word is what would collide; and **any query touching league rank carries the validity filter** (group `>= min_valid_group_size` **and** `weekly_xp > 0`) because `league-finalize.ts` writes `final_rank` for every member of every group, including ones the UI itself calls non-competitive — without it, most accounts' first medal would be minted for doing nothing. `visibility` decides what an unearned badge looks like: `always` (grey, with its criterion), `mystery` (a «؟» tile that leaks nothing — the server strips the name, icon and copy), `earned_only` (absent entirely, for a condition nobody can meet any more). **The granted class** (migration 0037): a badge whose metric is `grant:<its own key>` — «همراه» (key `companion`) is the first — is founder-GIVEN, never earnable: what is written is the decision (one `badge_grants` row via `POST /admin/badges/grant`, form on the `GET /admin` page; revoke with `POST /admin/badges/revoke`, read with `GET /admin/badges/grants?user=`), and the badge stays derived from it (`plus-api/src/services/badge-grants.ts` + the generic `grant:*` fold in `achievements.ts`) — the same move «ستون» makes with the payments ledger. Granting is idempotent per (user, badge) and a repeat press mints nothing; the optional one-time discount rides along as an ordinary `discount_grants` row written in the same transaction (the conventional bug-report thank-you is ٪۵), because granted badges are always `earned_only`, single-level, and never carry a `discount_percent` of their own. Tests: `plus-api/test/badge-grants.test.ts`. **«ستون» (key `pillar`) is the one badge with an entitlement outside the wall**: the first paid subscribers renew 20% cheaper, forever, at any price. `PILLAR_SEATS` is 51 — fifty seats for readers plus the founder's own gateway-paid account — while every public word stays «پنجاه», which remains true for the readers it is promised to. The seat definition lives in `plus-api/src/services/pillar.ts` and everything reads THROUGH it — the badge metric, `startPayment`'s discounted amount, and `GET /pay/plans`'s personalized prices — never re-derive it elsewhere. A first purchase is never discounted (the seat is minted by it), and gift-card/admin/league premium mint no seat (only `payments` rows do) — **with one exception, the founder's own grant** (`pillar_grants`, migration 0038; `POST /admin/pillar/grant`, undone by `POST /admin/pillar/revoke`), for somebody who helped build this and was never going to appear in a payments ledger. It is the same move the granted class above makes, one layer down — what is written is the DECISION, and the seat stays derived from it — but it is its own table rather than a `badge_grants` row, because a seat is not only a badge: it is a rank among the fifty and a price at the till, and both have to keep coming from one query. It is deliberately a row BESIDE the ledger and never a forged `payments` row, which would lie to revenue, to the gateway's monthly ceiling and to the discount-credit join; both sources are ranked in ONE query (`SEAT_CLAIMS` in `pillar.ts`); a grant is written today so it sorts after every seat already taken and **moves nobody**; it SPENDS one of the 51 rather than growing the count (fifty readers hold seats either way, which is what keeps the public «پنجاه» true); an account holding both claims keeps the earlier one, so paying later never mints a second seat; and it is the one seat that is revocable, because a gift is not a receipt. Two consequences to say out loud: a granted holder's FIRST purchase is discounted too (the seat predates it — that is the gift), and they get the same «تو ستون شدی» welcome, sent by the grant endpoint unless it is called with `welcome: false`. **Its fill state is a secret**: the badge is `earned_only` from day one and no reader-facing surface ever says whether seats remain, because either answer is a subscriber count ("open" = under 50 paying accounts, "closed" dates the fiftieth) — closure is automatic (`isPillarSeat` stops at 50, no commit, no announcement), the campaign lives in the founder's own marketing, and the ONLY surface reporting the roster is `GET /admin/pillar`; never add an open/closed signal to the wall or the pricing page. **The wall also carries money — one-time discount credits** (`plus-api/src/services/discount-credits.ts`, migration 0031): a leveled badge reaching **silver mints ٪۱ and gold ٪۲** off ONE future purchase (`discount_percent` on the level in `badges.json` — retuning it is a commit, like every threshold), while bronzes, one-shot badges and the mysteries deliberately mint nothing (paying for «ققنوس» would be paying for the broken streak, and a value tag on a «؟» tile would sell its secret). The engine is deliberately GENERIC: `discount_grants` rows are the same credits minted by founder decision — a birthday, an Eid campaign — via `POST /admin/discounts/grant` (read back with `GET /admin/discounts?user=`), so "later we discount other things too" is a row insert, not a feature. Four rules guard the money: **credits applied to one purchase never exceed `CREDIT_CAP_PERCENT` (10)** and a credit that doesn't fit is skipped whole, kept for the next purchase — never sliced, which is exactly why a GRANT above the cap is split into several credits at grant time (`splitGrantPercent`, used by both writers: ٪۲۰ is written as two ٪۱۰ and spent one per purchase) — a single oversized row would be skipped on every purchase forever while `POST /admin/discounts/grant` answered `ok: true`, so the founder types the total they mean and the ledger holds what the engine can actually pay out; **the «ستون» ٪۲۰ stacks ON TOP of that cap** (a seat-holder with full credits pays ٪۳۰ less) and is itself never consumed; **badge credits are DERIVED at purchase time** from the same facts the wall reads — only the CONSUMPTION is written (`discount_redemptions`, tied to its `payments` row: spent = payment `pending`/`paid`, so a failed/canceled payment releases its credits by the join alone, no cleanup path); and **the credit engine may never take the shop down** — `startPayment` guards it with a catch and sells at list price if it fails. Surfaces: the strip above the wall + per-disc value pips + per-level chips (`achievements.js`, from `GET /achievements`'s `discount` block and per-level `discount_percent`/`discount_state`), the celebration card's one extra line (`discount_percent` in `pendingAnnouncements`), and `GET /pay/plans`'s `onetime_discount` beside `pillar_discount` (pricing-page notice says «با همین خرید مصرف می‌شود» BEFORE the pay button). Tests: `plus-api/test/achievements.test.ts` + `achievements.dom.test.ts` + `discounts.test.ts` (+ the «ستون» blocks in `pay.test.ts` and `admin.test.ts`).
- **`plus/des-scores.json` — DentCast Evidence Score (DES), and its display contract.** The spec is `.dentcast/dentcast-evidence-score-v1.5.md`; the publish step that produces a record is workflow **4.13** (armed by Phase B **Question 4.8**). Same machinery as `pathways.json`/`badges.json`: versioned in the repo, agent-written, no API deploy to change. The file is keyed by `content_id` (page path, no leading `/`, no `.html`) → `{scored_at, sources:[…]}`, and **`sources` holds the spec's output objects verbatim** — the spec owns that shape. **Nothing derivable is stored beside them** (no wrapper `band`, no `track`, no display strings): `content_type`, `band`, `question_type` and `provisional` already live inside each object, and a second copy is a second source of truth. It is **not** a brain field — Hard Rule 5 forbids adding one, and that is why this file exists at all. An absent `content_id` is how the display knows there is nothing to show, so a skipped publish writes **no key**, never a placeholder. **DES display rules** (mockups approved 2026-08-14): two placements and no others — a thin **chip** under the lead beside the date, and an **evaluation card** after the body and before the source citation; nothing mid-prose and nothing floating. The band is drawn as **five discrete blocks E→D→C→B→A with only the current one coloured**, never a gauge or a continuous bar, because the output is not continuous and a needle would give a two-point difference a meaning it does not have. **`question_type` is welded to the band and never shown apart from it** — bands are comparable only inside one question type, so an A on a bench test and an A on a clinical trial come from two different tables and must never read as equal. The 0–100 number rides **small and dim beside the band, never as a headline**: the band is what a reader judges with, the number is the audit layer. An `ABSTRACT_ONLY` score (`provisional: true`) wears a **hatched** block plus an «امتیاز مقدماتی» tag rather than a solid one. **DentCast's own authored content gets no band bar at all** — a «تجربهٔ بالینی» badge with its transparency score (e.g. ۱۷ از ۱۹) and the four transparency criteria, with band E kept behind a details toggle rather than deleted. Colour is its own third scale, **grey → dark green, never through red** — E is grey, not red, because a low band is not a failing grade and must not read as «رد شده»; it is never amber (that means «this is what a subscription buys») and never brand blue. Every element (chip, band, question type, number, provisional tag, transparency criteria) explains itself in a short popover. **No page carries DES markup** — same rule as the article action row, so the renderer is a shared module reading this file, and step 4.13 writes data only. Homepage carries a standing explainer box (`#dcDesLegendBtn`, mobile shell, after the trust strip) so a reader meeting a badge on an article already knows what it is.
- **کد معرف — referral codes** (`plus-api/src/services/referrals.ts`, migration 0044; design ledger `.dentcast/referral-handoff.md`). Every signed-in account may mint ONE code — a lowercase-ASCII alias (`^[a-z]{4,16}$`, no digits, no Persian — the same ی/ي، ک/ك، ZWNJ problem `hl-view.js`'s `foldFa` exists for) plus the last two digits of the owner's own mobile, e.g. `dentmaster61` (a phone-less, Telegram-first account gets two RANDOM digits instead — cosmetic only, uniqueness is on the WHOLE code). **Permanent, never renamed, never re-minted** — the code goes out on WhatsApp/stories and a mutable one either breaks those links or lets someone hijack a freshly-shared code. Whoever enters it **on the pricing page, on their own first purchase** gets ٪۱۰ off; the code's owner gets ٪۵ one-time credit — but only once the referred account has an actual `payments` row with `status='paid'` (the sole anti-farming rule; a code alone mints nothing). **No new discount engine**: کد معرف is a THIRD source for `services/discount-credits.ts`'s `DiscountCredit` (`kind: 'referral'`, alongside `badge:`/`grant:`), read through the exact same `CREDIT_CAP_PERCENT`-capped `availableCredits()`/`pickCredits()` every other credit goes through — so it stacks with badge/grant credits under the same ٪۱۰-per-purchase ceiling, and with «ستون»'s permanent ٪۲۰ ON TOP of that ceiling (a referred seat-holder can hit ٪۳۰). What is WRITTEN is one `referrals` row (X referred Y) — both percentages are derived from it, EXCEPT the percentages themselves are stamped onto the row (not read from the `REFERRED_DISCOUNT_PERCENT`/`REFERRER_DISCOUNT_PERCENT` constants) so a future retune cannot retroactively shrink credit already earned. `referrals.referred_user_id` is UNIQUE — one referral per account, for life — and a referred account may only claim a code on ITS OWN first purchase (any prior `paid` row refuses every code, including an unused one). `POST /pay/start`'s `referral_code` is claimed by `services/payment.ts`'s `startPayment` BEFORE `availableCredits()` runs, outside the credit engine's own failure-swallowing `catch` (an invalid code is the customer's mistake — 400 — not a silent full-price sale); `GET /pay/plans?ref=` only PREVIEWS (`checkClaim`, never `claimReferral`) and is ignored for a signed-out visitor, so the route can never be used to enumerate the code space. The referrer sees **counts only, never who** (`GET /referral`'s `used_count`/`purchased_count`/`earned_percent`) — the same discretion `up-board` and پشتیبانی's public threads already practice. `services/merge-profiles.ts` MUST carry `referral_codes` + both `referrals` id columns (cascade-deletes off `profiles` otherwise silently erase real credit) and must delete — not merely repoint — any row that a merge would turn self-referential, since Postgres enforces `check (referrer_user_id <> referred_user_id)` per-row, immediately, with no fixing it up after the `UPDATE`. Surfaces: the profile's «کد معرف» section (mint form with a live-preview + explicit irreversible-commit confirm, or the code + copy + share-link + stats once minted) and the pricing page's کد معرف box between the plan grid and the buy button — `?ref=` deep-links pre-fill it, and a sign-in-to-pay round trip persists the typed code into the URL first so `location.reload()` cannot burn it. Tests: `plus-api/test/referrals.test.ts`.
- **پشتیبانی — support tickets** (`plus-api/src/services/support.ts`, migration 0041). The first channel that carries a reader's words INTO the site: everything the notification layer did before pointed one way (اطلاعیه, push, the founder broadcast), so a reader with a question had the contact page and nothing else, and the answer happened in a messenger where it belonged to nobody. **Who may open one is decided by the KIND, never by the plan.** Gating the whole feature behind premium reads well until you follow one case: the person asking for a student discount is asking BECAUSE they are not premium, so a premium-only door refuses the one ticket that could earn a subscriber. `POST /pay/gift` settled this already — `requireAuth`, never `requirePremium`. So `billing`/`student`/`bug` are open to any signed-in reader; `support` (the open-ended one) stayed premium but left `FORM_KINDS` on 2026-08-12 — the premium question path is now گفت‌وگوی زیر مطلب, and `support` survives in `TICKET_KINDS` only so `kindTitle()` keeps resolving tickets opened before that change. `GET /support/kinds` still reports `locked` per kind (now moot for every kind the form offers — nothing on it is premium any more). `support_tickets.has_photo` (migration 0043) is a claim the reader makes, not a derived fact — the same kind of column as `status` — set by the optional «عکسی دارم» tick on the form, and it is what lets both queues show a «📎 عکس در راه» flag instead of the photo arriving as a surprise. **A second payment rail — واریز به شبا (bank transfer) — rides the SAME `gift_redemptions` table the gift-card rail already used** (`kind='bank_transfer'`, migration 0043's `amount_rial` column, the one-pending-claim index now scoped PER KIND rather than globally): `POST /pay/bank-transfer` computes the amount server-side from `PLAN_PRICES_RIAL` and never trusts a client-sent figure; approval reuses the same `approveRedemption`/`rejectRedemption` the gift-card queue already calls; and the admin panel's «تأیید + اهدای نشان دانشجو» button (`POST /admin/bank-transfer/approve-with-badge`) approves the claim, extends the subscription and grants the `student` badge in ONE transaction (`activateMonths`/`grantBadge` both now take an optional external client for exactly this). The photo goes to a messenger with `T-ABC-DEF` typed under it and `GET /admin/support/by-reference/:ref` is what turns that into an account — the same move gift-redemption makes with a card code, and the reason to **delete the photo once verified and keep only the decision**. Founder surfaces are the «صندوق پشتیبانی» block on the rendered `GET /admin` page (queue ordered so whoever waited longest for a human is first, thread + reply + reply-and-close inline, plus the reference lookup) over `GET /admin/support`, `POST /admin/support/:id/reply|close|reopen`. Reader surface is `/plus/support.html`; its gate is deliberately NOT the premium gate every other `/plus` page uses — signed-in always gets the real view. A reply notifies with the `support_reply` kind, which is **UNCAPPED** in `notify-policy.ts` on the renewal warning's reasoning: this is the answer to a question the reader asked, and a streak nudge that arrived first must not be why it never lands. `SUPPORT_ALERT_PHONE` pings the founder on a new ticket (empty logs a line — an alert nobody can receive never fails a reader's write). Tests: `plus-api/test/support.test.ts`. **گفت‌وگوی زیر مطلب — threads under an article** (migration 0042) are the same object with an anchor, not a second system: `content_id` on `support_tickets` IS the discriminator (null = written from the support page), so one queue, one reply path, one notification kind. Four consequences the code depends on: **one reader + one page = ONE conversation** (partial unique index on `(user_id, content_id)`; a second comment continues the thread, and a closed one reopens), **article threads do not spend the `MAX_OPEN_PER_USER` support budget** or commenting would quietly lock somebody out of reporting a payment problem, **`GET /threads/public` is the only endpoint in `routes/support.ts` with no session** — a published thread is part of the page, so it lives OUTSIDE the encapsulated scope, because a `preHandler` applies to every route in its context regardless of registration order and "declare it first" is not a way to keep a route public — and **the author is their `display_name`**, which defaults to a generated Persian pseudonym, which is what makes publishing safe to offer at all. - **اطلاعیه — the in-app inbox** (`plus/js/notices.js`, `plus-api/src/services/notices.ts`). Every notification the API produces already passed through exactly ONE function — `sendCapped` in `notify-policy.ts`, "the one door every outgoing notification goes through" — so the inbox is that door also WRITING the message, with its text, to the same `notification_log` row it already counted. Seven kinds got an in-site home without one of their services being touched. It fixes two things that were not visible as bugs: a reader who granted no push permission and linked no messenger received **nothing** (the providers no-op quietly for a user with no destination), and the daily cap **dropped** the overflow rather than queueing it, so a busy day lost news even for readers who did have a channel. Now the cap only decides whether a message TRAVELS; it always lands. **The one rule the whole thing rests on: `delivered` separates the table's two jobs, and every query that asks "was this sent" carries it** (`sentCountOn`, `alreadySentKindOn`) — the table is also the cap counter, so counting in-app-only rows would let the cap feed itself and silently starve a user's push budget. The inbox line is deliberately SHORT and is not the Pulse («مطلب جدید در {بخش}» + the article's title): a paragraph about the argument belongs on a lock screen, not in a row people scan. The pushes that follow then pass `inbox: false` to `sendCapped` so one publish is never shown twice — they still write their (title-less) counter row, because the row *is* the cap counter. And **`POST /admin/notices/broadcast`** is the founder's own announcement, with a form on the rendered `GET /admin` page: the inbox row always lands instantly, while `push` respects the awake window unless forced — «uncapped» was about a broadcast not eating a reader's budget, never a licence to wake people at 03:00. **`POST /admin/notices/user`** is the same door for ONE reader — the note a broadcast could never carry, since a broadcast's narrowest audience is a whole tier and thanking one person with it would tell every premium reader they were thanked. The اطلاعیه row lands instantly at any hour (it is a row in a table; no phone can be woken by it), `push` respects the awake window unless `force`, and the `system` kind keeps a personal note out of the reader's daily push budget. - **Collections** (premium Phase 3; spec §4's `collections`/`collection_items`, provisioned since migration 0001, live since migration 0012's indexes). Unlike a pathway (founder-curated) or a topic archive (auto-grouped by taxonomy), a collection is **entirely the user's own** — any mix of their own highlights and whole pages, no taxonomy coupling. Backend: `plus-api/src/routes/collections.ts` (full CRUD + idempotent item-add, all `requirePremium`). Frontend: `/plus/collections.html` (catalog), `/plus/collection.html?id=` (items, rename, delete), a "کالکشن‌ها" block on the `/plus/` dashboard, and the **"افزودن به کالکشن"** entry points — a dual-target toolbar button in the workbench (selected highlight, or the whole page if none is selected — same pattern as the یادداشت button) and a per-row button on the dashboard's recent-highlights list. All three go through `plus/js/collections.js`'s `openCollectionPicker()`, which also owns the free-tier gate message (shown on click, not a locked page). A **pin is a card, not a link** — same rule as the library, and it carries the same content (the mark, the note, the label) plus its own actions: inline edit, copy, **انتقال** to another board, «متنِ مقاله ›» (`?dcphl=`), and remove. Move needs no endpoint: `openCollectionMove()` adds to the target and then calls the board's own remove, and the add is idempotent at the DB level, so a half-finished move leaves the item in both boards, never lost. The catalog carries search + sort (تازه‌ترین/آخرین افزوده/پرمورد‌ترین/نام) and each board card shows `item_count` + `last_item_at`, which `GET /collections` **derives** (`max(ci.created_at)`) rather than storing — no column, no migration, no write path to keep true. A board page filters by kind (هایلایت/صفحه) and text. Both surfaces share `hl-view.js`; the chooser sheet (`chooserCard`) is one component used by both "add" and "move", and grows a filter box past six boards. Migration **0018** adds a board's own identity (`emoji`/`color`/`description`, all optional — a board with none renders exactly as before) and `collection_items.position`: **NULL means "never arranged"**, so an untouched board still opens newest-first, and `PUT /collections/:id/items/order` writes the **whole** order at once (empty array clears it), which is why there is no half-arranged state and a retry is a no-op. Arranging is a *mode* in the UI (`⇅ چیدمانِ دستی`): it collapses the masonry to one column, hides the filters (↑/↓ over a filtered subset would move an item past cards that aren't on screen) and gives each pin ↑/↓ + «۲ از ۷» — buttons, not drag, because dragging a masonry card is unusable on a phone and invisible to a keyboard. Migration **0036** (renumbered from the handoff's 0035 — `0035_ai_card_state` merged first and owns the number) adds two pin kinds a board originates itself («افزودن پین» chooser on the board header) plus board export — design ledger in `.dentcast/collections-pins-export-handoff.md`, whose decisions are made, not open: a **«متن خودم» text pin** and a **«رفرنس» reference pin** live in the `snippets` table (NOT "notes" — `article_notes` owns that word; one row, many pins via `collection_items.snippet_id`, a third partial unique index, and a one-kind XOR check), created-and-pinned atomically by `POST /collections/:id/snippets`, edited via `PATCH /snippets/:id` (kind immutable), re-pinned/moved through the same `POST .../items` with `{snippet_id}`. A reference's DOI metadata is fetched from Crossref **in the user's browser** (the container's international egress is unreliable; the API only stores what it's given) and manual entry is a first-class path, not a fallback — Persian journals mostly have no DOI. The **orphan rule**: removing a snippet's LAST pin deletes the snippet in the same transaction (there is no snippets library page, so an unpinned snippet would be invisible-but-alive forever); «انتقال» never trips it because it adds to the target before removing. No new XP kinds (pins fire the existing `collection_item_added`; «گنجینه» counts them automatically), and `GET /export/highlights` dumps `snippets` on ANY plan (data ownership). **Board export** («خروجی» on the board header): `GET /collections/:id/export?format=docx|pptx` builds the file server-side in memory (docx + pptxgenjs, pure JS, streamed, no temp files on the ephemeral disk) in the board's own display order — چیدمانِ دستی IS the slide/handout order. References collect into a numbered «منابع» section (Vancouver-ish, same `withDot` guard as the client's کپی‌استناد); RTL is per-paragraph (`bidirectional`/`rtl="1"` + right alignment on Persian, plain LTR on Latin citations). pptx passed the handoff §4.3 real-file gate on 2026-08-10; known accepted blemish: Google's Docs/Slides viewers ignore the rtl flag (bullets render left there) while real PowerPoint honors it. Deploying any of this needs an **API container rebuild** (new npm deps + migration 0036), not a content refresh.

## Site-wide invariants

- **Google Analytics 4 (deferred) on every page.** Every HTML page MUST carry the deferred GA4 snippet (measurement ID `G-GMM0WC8X3M`) inside `<head>`. It is lazy-loaded — `gtag.js` is appended only after the `load` event so it never blocks first paint. Do NOT use Google's default async snippet; use the deferred pattern below. Because new pages are cloned from the most recent same-category page, the tag propagates automatically — but always confirm it survived the clone.
  - The canonical injector is `.github/scripts/inject_ga.py` (idempotent; skips pages that already have it, and pages without a `<head>`). To backfill/verify the whole site: `python3 .github/scripts/inject_ga.py` (or `--check` to fail if any page is missing it).
  - The build templates emit it too: `GA_DEFERRED_SNIPPET` in `tools/build_episodes.py` and `tools/build_pillar.py` (and the glossary head literal). Keep all of these in sync if the snippet ever changes.
  - The `.org` and `.ir` codebases are mirrors; the same tag intentionally deploys to both. Do NOT add per-domain logic.
  - The exact deferred snippet (place inside `<head>`):
    ```html
    <!-- Google Analytics (deferred: loads only after the page is fully rendered) -->
    <script>
      window.addEventListener('load', function () {
        window.dataLayer = window.dataLayer || [];
        function gtag(){ dataLayer.push(arguments); }
        window.gtag = gtag;
        gtag('js', new Date());
        gtag('config', 'G-GMM0WC8X3M');
        var ga = document.createElement('script');
        ga.async = true;
        ga.src = 'https://www.googletagmanager.com/gtag/js?id=G-GMM0WC8X3M';
        document.head.appendChild(ga);
      });
    </script>
    ```
  - If a Content-Security-Policy is ever added, it must allow `script-src https://www.googletagmanager.com` and `connect-src https://*.google-analytics.com https://*.analytics.google.com`. (No CSP currently exists in this repo.)

- **API preconnect on every page.** Every HTML page carries
  `<link rel="preconnect" href="https://api.dentcast.ir" crossorigin>` and the
  same for `.org`, at the very top of `<head>`. This is a paid-sponsor
  correctness issue, not a micro-optimisation: the Spot card cannot render
  until `/me` answers (that gate is what makes "premium sees no ads" true, and
  it is **not** to be relaxed), so on the first page of a tab the cold DNS +
  TLS handshake sat directly in front of the sponsor's impression — measured
  2.7–3.0s to first card, against 70–170ms on a refresh. Preconnect moves the
  handshake into HTML parsing instead.
  - Injector: `.github/scripts/inject_preconnect.py` (idempotent; `--check`
    fails if any page is missing it). `tools/build_pillar.py` emits
    `PRECONNECT_SNIPPET`; `tools/episodes_template.html` carries it inline.
  - **`crossorigin` is required and not decoration** — the API is called with
    credentials, and a connection opened in anonymous mode is not reused for a
    credentialed CORS request, so dropping it silently undoes the whole thing.
  - Both hosts are listed on every page on purpose: the two codebases are
    mirrors and per-domain logic is forbidden. The unused socket is idle and
    the browser drops it.

- **Amber is the PREMIUM colour — one colour, one meaning.** Amber/gold
  (`#c9922b` on light, `#e3b849` on dark; the older `#c49820` is the same
  family) marks **what a subscription buys, and nothing else**: the locked
  feature cards under «دنت‌کست پریمیوم» on the homepage, the «🔒 ویژه‌ی
  پریمیوم» badge, and the premium library card in the archive. Everything
  else keeps the site's blue. Two consequences worth stating, because both
  have already been gotten wrong once: the **Pulse** is news, not premium, so
  it stays blue however tempting its historical amber is; and **«دنت‌کست
  پلاس» is the FREE video section, not the paid tier** (پلاس = free
  signed-in, پریمیوم = paid), so its chip must never wear amber. The tokens
  live in `index.html`'s `<style id="dcDepthTheme">` (`--x-amber*`); a
  premium surface gets a wash that fades out in its top 45% plus an amber
  hairline — never a solid amber card, which would read as a warning.

- **The article's action row — ONE row above the prose, and no page owns it.**
  `#dcActionRow` (`.dc-actions`) holds everything that used to sit between the
  title and the first paragraph. Until 2026-08-12 that area was **four
  independent bands from four injectors** — dc-nav.js's reading-time/share chip
  row, votes.js's قلب line, dc-nav.js's ToC, plus.js's میز کار bar — each doing
  its own `insertBefore(firstBox)`, so their **order was an accident of script
  load order** and their alignments (centre/centre/full-width/right) and button
  sizes agreed with nothing. Two groups, and the split IS the design:
  **`.dc-actions-main`** is what you can DO with the page (میز کار › افزودن به
  کالکشن › پسندیدم, in that order), **`.dc-actions-aux`** is what the page says
  about itself (زمان مطالعه) plus one courtesy (اشتراک‌گذاری). Five rules the
  code depends on. **No page carries this markup** — zero of the 197 article
  pages does, which is exactly why tidying the area cost no page edits and why a
  future change to it must stay in shared files. **Two builders, either order,
  both find-or-create**: `dc-nav.js` phase 7b builds the shell and fills the aux
  group (it is the only thing on the page that can count words before the module
  graph loads); `plus.js`'s `ensureActionRow` fills the main group, and builds
  the whole row itself on the desktop shell where dc-nav.js is stripped out of
  the fetched article. **The styles live in `plus.css`, never `dc-article.css`** —
  the shell keeps the former and strips the latter, and one row may not be
  defined in two stylesheets. **One button vocabulary** (`.dc-act` + a modifier:
  `-primary` filled, `-outline`, `-quiet`, `-heart`), same height and shape for
  all of them, so only weight and colour say which matters more — three
  different pill sizes in one row is precisely what read as clutter. And
  **زمان مطالعه is not a button**: as a `.dc-meta-chip` it was visually identical
  to the share pill beside it and a reader had to press it to learn it did
  nothing. The **ToC stays its own card**, below the row and above the prose — it
  is the one thing in that area that is content rather than a control. And the
  area has **three** anchors in `config.js`, not one: `findProseBox()` (the first
  box) for what goes ABOVE the article, `findProseRoot()` (the body as one
  element) for measuring, `findProseEnd()` (the last box) for what goes BELOW.
  On every page whose body is a single box all three agree, which is why picking
  the wrong one stays invisible — گفت‌وگوی زیر مطلب shipped anchored on
  `findProseBox()` and read correctly on 400-odd pages while opening after
  section 1 of 8 on the 26 legacy NoteCast pages. `findProseRoot()` is not the
  fix for that either: on exactly those pages it is `main.article-content-wrap`
  itself, so inserting after it lands outside the article shell. **Audio
  episodes get a SHORTER row of the same kind** — قلب + اشتراک‌گذاری, no میز کار
  (there is no workbench for a podcast) — built by `initEpisodeActions()` on the
  standalone page and by `mountArticleWorkbench`'s episode branch on the desktop
  shell — and the same two callers give an episode its **گفت‌وگوی زیر مطلب**,
  which had reached articles only because `initArticle()` mounts it and
  `initArticle()` bows out at the audio player. Nothing ever excluded a podcast:
  the block is written against a `content_id` and the API gates on nothing else,
  so it was unreachable rather than forbidden. Its anchor there is the single
  `.ep-box`, which puts the conversation under the whole episode card and above
  the ‹قبلی/بعدی› nav. Until 2026-08-12 they were the only content on the site a reader could
  not press پسندیدم on, while sitting in up-board's catalog like everything else
  (210 of its 444 entries) and earning engagement the score already counted
  (`episode_listened`). Nothing was added to `tools/episodes_template.html` for
  it: a row in the template would mean rebuilding 209 files for what the shared
  module puts there for free.

- **E-NAMAD trust seal (نماد اعتماد الکترونیکی) — three placements, dentcast.ir only.** The seal lives on exactly three surfaces and is **not** a per-page element: `index.html`'s `<footer>` (mobile shell), `index.html`'s `.dcd-a-seal` row in the col-A sidebar (desktop shell, where that footer is `display:none`), and `about.html`'s `.dc-trustseal-box` under the contact card. Do **not** clone it onto content pages — every copy is a request to enamad's server for zero trust value on an article page.
  - **This is the one deliberate exception to "no per-domain logic".** The seal is issued for a single domain (ours: `dentcast.ir`) and `trustseal.enamad.ir/logo.aspx` renders from the request's referrer, so on the `.org` mirror it answers with an *invalid seal* image. Two layers gate it: an inline `<head>` guard in both pages sets `dc-no-seal` on `<html>` off `.ir` (hides it before the body parses, no flash), and a block at the end of `dc-nav.js` removes the node outright. The images are `loading="lazy"` and both seals sit below the fold, so on `.org` the request normally never fires.
  - **The `<a>`/`<img>` attributes enamad verifies are copied verbatim and never rewritten** — `referrerpolicy='origin'`, `id`, `Code`, and the `code` attribute on the `<img>`. Only `alt`, `loading` and the wrapper are ours. The markup ships **statically in the HTML** (never JS-injected) so enamad's own crawler reads it.
  - Styling is `.dc-trustseal` in `dc-theme.css`, mirrored into `index.html`'s inline `<style>` (index loads no shared CSS). The chip is white in **both** themes on purpose — the seal artwork assumes a light background — and its box is fixed-size so nothing shifts when the image lands.
  - The desktop shell's reader strips `.dc-trustseal` along with the rest of the page chrome (`index.html`, chrome-removal selector list): `dc-nav.js` is stripped from that document, so a seal inside the iframe would escape the host gate.
